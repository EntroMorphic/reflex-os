## [Unreleased]

### Changed

- **Tier C's plan said two blockers; one has been closed for some time.** `reflex_task_reflex.c` and the Kconfig help both stated the scheduler has no working tick — that nothing routes SYSTIMER through the interrupt matrix, gives it a PLIC priority or sets the `mie` bit. `reflex_sched_tick_start` does all three, and `make tick-measure` reports **5/5 verified cold starts at exactly 1000 Hz** on the independence build. Both documents now say so, because they gate the C3 cutover and were overstating the distance.

- **A comment in `reflex_sched.c` claimed the tick was measured "on both the default and the 802.15.4 builds".** Re-measured: 5/5 at 1000 Hz on the independence build, **0/5 on the default**, where the routing reads back entirely correct — matrix entry, PLIC enabled, priority above threshold, `mie` set, SYSTIMER asserting and latched — and nothing is delivered. The console's interrupt was ruled out as the cause: console on CPU line 10, tick on 11. The Wi-Fi stack is the obvious next suspect and has not been investigated. Corrected to what was measured.

  What remains for C3 is the blocker that was always the larger one: **nothing starts the scheduler**, and behind it a `setjmp`/`longjmp` context switch that is undefined behaviour for starting a task on a fresh stack, plus `mtvec` ownership across nine live ESP-IDF interrupt lines.

- **The watchdog "recovery net" does not recover the board. Arming is disabled by default.** The premise was that the low-power watchdog, armed before a sleep, turns "never wakes" into "reboots a few seconds later" and so makes owning the sleep entry survivable. It fires exactly as configured. It does not return a usable board, and both stage actions fail differently:

  - `RESET_RTC`: after firing once, the board reset every five to eight seconds indefinitely. The watchdog itself read back **disarmed**, so the loop was the state it had left behind, not the watchdog re-firing. Only reflashing recovered it — twice.
  - `RESET_SYSTEM`: the board did not come back at all. No shell, and esptool could not connect either — *"Failed to connect to ESP32-C6: No serial data received"*. It needs a physical power cycle.

  So the mitigation designed to make sleep ownership safe is itself the thing that stranded a board, which is precisely the failure it existed to prevent. Arming now requires `-DREFLEX_WDT_EXPERIMENT=1`; reading and disarming stay available, and the boot-time disarm protects a board armed by such a build.

  **Owning `esp_sleep.h` is therefore still blocked, and now for a better-understood reason:** not the difficulty of the entry sequence, but the absence of any demonstrated way to survive getting it wrong. That is the problem to solve first, and the watchdog is not the answer to it.

- **The boot-time disarm moved from the shell to the first statement of `app_main`.** At the shell it was far too late: boot reached `[reflex.kernel] supervisor: policy=registered` and the port dropped, so the watchdog fired again during init every time and the loop could not be broken, because no command could be typed. ESP-IDF's own startup disarms it at the same point and for the same reason.

- **`kernel wdt` enforces a 3000 ms floor.** Below the time it takes to reach the disarm, a timeout guarantees an unbreakable loop.

- **The RC_SLOW figure is measured, not asserted.** An earlier comment claimed it was "calibrated by measurement" when nothing had calibrated it. Asked for 5000 ms the watchdog fires at about 5300 ms, three consecutive trials agreeing, so the oscillator is nearer 128 kHz than the nominal 136 kHz and timeouts run ~6% long. The constant is deliberately left nominal: firing late still recovers a board that never woke, firing early resets one that was working.

### Changed

- **Tier C's floor is 4, and half of it is Tier D's.** Recorded rather than renamed. The four entries are `intr_handler_set` (twice) and `intr_handler_get`/`intr_handler_get_arg`, and every tempting fix — `--wrap=intr_handler_set`, calling `_global_interrupt_handler` directly — leaves ESP-IDF's `s_intr_handlers` table exactly where it is and only changes which symbol names it. That would have been the fourth rename this measure accepted; it is refused.

  `intr_handler_set` registers Reflex's dispatch with ESP-IDF's vector so Reflex's interrupts are delivered *before* Reflex takes `mtvec` — which is what lets the entry path prove the tick under ESP-IDF's vector and hand the machine back if it is dead. That check has caught a real failure twice; removing this dependency means giving it up. `intr_handler_get`/`get_arg` read ESP-IDF's table to service drivers Reflex does not own, and measured on the own-entry build that is exactly **one** driver: the PLIC has three live lines (`0x00000d00`) — 10 the tick and 11 the console, both Reflex's, and 8 the 802.15.4 MAC, the only ESP-IDF component allocating an interrupt in this build.

  So Tier C ends when Reflex owns the radio, and the radio's own floor is a 178 KB PHY blob. The two tiers are one problem.

- **Retracted: "Tier C is clear."** Removing the `freertos/portmacro.h` include removed an include; it did not remove the dependency. `check_independence.py` read `#include` lines only, so anything reached by a local `extern` was invisible — and `intr_handler_set`, `intr_handler_get` and `intr_handler_get_arg` are ESP-IDF C in `components/riscv/interrupt.c`, declared locally here. A comment in `reflex_hal_esp32c6.c` claimed they live in mask ROM; no linker script PROVIDEs them, and that false claim is what let a borrowed interrupt layer read as a hardware fact. Reflex's allocator registers into ESP-IDF's `s_intr_handlers` and `reflex_trap_handler` reads it to dispatch every interrupt Reflex does not own.

  One of those declarations was added in this very work, with the reason in its own comment: *"which would add an ESP-IDF header to this file for two symbols and move the independence count in the wrong direction."* The metric was gamed and the gaming was documented.

  The checker counts externs now — ROM prefixes uncounted because ROM is silicon, the project's own symbols and `__wrap_`/`__real_` machinery excluded, everything else required to be named in `EXTERN_TIERS` or rejected as unclassified. Honest numbers: Tier C **8** for `build_independence` and **4** for `build_own_entry`; on-path totals **14** and **10**. The baseline records it as a measurement correction, not a deliberate increase — nothing got worse, the tool started seeing what was already there.

  Third structural hole found in this measure: it counted subtraction and missed capability, it was aimed at a configuration that was not the one making the claim, and it could be satisfied by moving a declaration.

- **The supervisor became backend-agnostic, which stands.** On-path total 6, down from 7 by the old measure, with three tiers clear (A, C, E) — *by that measure*.

  The last dependency was one include in a file whose entry point never ran there — `reflex_freertos_compat.c` reached `freertos/portmacro.h` for `configMAX_PRIORITIES` and the TCB offsets, and existed to wrap `xPortStartScheduler`, which `REFLEX_OWN_ENTRY` never calls. **Dropping the file would have scored as progress and silently stopped the policy engine**: `reflex_kernel_set_policy` has a weak no-op fallback in `goose_supervisor.c`, so the link would have succeeded and task-priority modulation would simply have stopped on the one configuration this work is for.

  Instead the supervisor delays through `reflex_task.h` rather than `vTaskDelay` — the one substitution that makes it backend-agnostic — and starting it is split into `reflex_kernel_start_supervisor()`, called by the FreeRTOS wrap where FreeRTOS starts and by `reflex_app_entry.c` where Reflex owns the machine. The TCB asserts and their header moved to `reflex_freertos_tcb_assert.c`, compiled only where FreeRTOS is the backend; a `#ifndef` around the include would not have removed the dependency, because `check_independence.py` reads include lines from source rather than running the preprocessor — correctly, since a guarded include is still a file the build must find.

  **A capability gained, not a count lowered.** The policy supervisor now runs under `REFLEX_OWN_ENTRY` where it previously did not: banner, `policy=1000ms supervisor=active`, `policy=registered`, and `reflex-kern` at priority 24 in `kernel tasks`. `make parity-diff` still reports zero regressions.

### Added

- **`make independence-own-entry` — the ratchet pointed at the configuration that makes the claim.** `make independence` measures `build_independence`, and that quietly became the wrong question: it does not set `CONFIG_REFLEX_TASK_BACKEND_REFLEX`, so it compiles `reflex_task_kernel.c` — the backend whose every function delegates to FreeRTOS — and carries its three `freertos/` includes. The own-entry build compiles `reflex_task_reflex.c` and starts no FreeRTOS at all.

  Measured: **10 on-path dependencies against 7**, Tier C **4 against 1**. The seven each have a name — `esp_heap_caps.h`, `esp_sleep.h`, `freertos/portmacro.h`, `esp_ieee802154.h`, `esp_flash.h`, `esp_flash_internal.h`, `esp_system.h`.

  And the one remaining FreeRTOS dependency is in a file whose entry point never runs there: `reflex_freertos_compat.c` includes `freertos/portmacro.h` for `configMAX_PRIORITIES` and exists to wrap `xPortStartScheduler`, which under `REFLEX_OWN_ENTRY` is never called. Excluding it from that build should take Tier C to zero. One include wide.

  Same shape as the defect the parity work fixed — there the measure counted subtraction and missed capability; here it is aimed at a configuration that is not the one making the claim.



- **The mtvec hand-off runs on hardware, and the Reflex scheduler executed tasks.** `kernel selftest` performs the whole sequence — route and arm the tick, tell the trap handler its CPU line, release ESP-IDF's stack-pointer watchpoint, quiesce every PLIC line but the tick, disable both timer-group watchdogs, take `mtvec`, start — and with FreeRTOS quiesced and Reflex's own vector installed, two tasks ran on the Reflex scheduler: `task A: tick 0 (sys=1)`, `task B: tick 0 (sys=1)`. C3's central question, answered on silicon.

- **`reflex_hal_intr_quiesce_except` / `reflex_hal_intr_restore`**, and **`reflex_hal_wdt_disable_timg`**. Reflex's trap handler deliberately does not acknowledge a line it does not recognise, so any ESP-IDF interrupt left enabled asserts, is never cleared, and stops the core; and both timer-group watchdogs are fed by FreeRTOS, so quiescing it makes them fire (`rst:0x8 (TG1_WDT_HPSYS)`) a few seconds after an otherwise clean start. Constants through the bridge, 178 -> 183.

- **The SoC scraper follows `derivedFrom`.** An SVD peripheral identical to another but for its base address carries no registers of its own, so `TIMG1.WDTCONFIG0` resolved as "absent from SVD" — true of the XML, false of the silicon. The bridge proving `TIMG1.WDTCONFIG0` equal to `TIMG_WDTCONFIG0_REG(1)` is what validates the handling.

### Fixed

- **The tick worked exactly once per boot.** On the independence build, in one boot: `998 Hz`, then `2 Hz`, then `2 Hz` — the first arming correct, every later one delivering a single tick and stopping. The cause was in `REAL_TARGET1`, the alarm the hardware actually matches on (`SYSTIMER + 0x7C/0x80`), which is maintained by the hardware in period mode and described by no other register. Read against the live counter it was immediate: arm 1 sat `+1463` ticks ahead, arm 2 `-19,182,014` behind — and arm 2's alarm was **exactly one period** past arm 1's, arm 3's exactly one period past arm 2's.

  So in period mode `COMP1_LOAD` does not set the alarm to "now + period"; it adds one period to whatever `REAL_TARGET1` already holds — and `reflex_sched_tick_stop` was clearing `TARGET1_WORK_EN`, which freezes it. Every re-arm placed the alarm one period past a timestamp from the previous run, and an alarm behind the counter matches once and never again. `tick_stop` now stops only the interrupt, not the comparator: **four consecutive arms in one boot measure 998, 998, 1000, 1000 Hz.** The cost is recorded in the code as a decision — the comparator runs while the tick is unused, setting `INT_RAW` into a status bit nobody reads, while everything that can reach the core is still released.

  Three fixes were tried on hardware before the cause was known and **all three failed**, named in `docs/independence-dependency-map.md` so they are not retried: ESP-IDF's `systimer_hal_set_alarm_period` ordering, re-latching `COMP1_LOAD` after enabling, and a one-shot absolute rebase (which broke the auto-reload outright — 0 Hz).

  Third defect of this shape in this work: a release that did not undo its acquire. This one was invisible until the register holding the evidence was found and read.

- **Seven HAL functions were declared in the shared header with no implementation on the classic ESP32.** The interrupt- and console-introspection surface added for the entry-point work went into `include/reflex_hal.h` — the contract for every platform — but only into the C6 HAL. The build survived purely because every caller happens to sit behind `CONFIG_IDF_TARGET_ESP32C6`, making it a link error waiting for the first one that does not. The same file already stubs `reflex_hal_stack_guard_disable`, `reflex_hal_wdt_disable_timg` and `reflex_hal_pwm_release` for exactly this reason, so this was a broken convention rather than a new question. Stubbed, and **mutation-checked**: removing one stub and adding a V3 caller produces precisely the predicted `undefined reference`.

- **A masked line stayed on the unclaimed list after it was claimed.** `reflex_hal_intr_alloc` did not clear the record, so the report was a list of lines that had once been unclaimed rather than lines currently lost, silently contradicted by the PLIC enable the same function writes. Cleared on allocation.

- **`unclaimed_masked` is zero by construction on an ordinary build**, because lines are masked only by `reflex_trap_handler`, which runs only where Reflex owns `mtvec`. Reported as such at shell start so the zero is not read as evidence the masking works — it is evidence only under `REFLEX_OWN_ENTRY`. The read-modify-write in `reflex_hal_intr_mask_unclaimed` also now states why it omits the `mstatus` bracketing every other writer of that register uses: trap entry has already cleared `MIE`, and it is callable from nowhere else.

- **`kernel tasks` prints the scheduler's slot table.** Task lifecycle was not observable from outside the scheduler, which is why a leak could be host-tested and not demonstrated on a board — with no way to see a slot, "the slot came back" is not a claim anyone can check. Shows state, name, priority, stack size and which slot is current, plus a count of dead-and-unreclaimed slots, since a dead slot can never be reused (`find_free_slot` takes `FREE` only). Observer role. On a build where FreeRTOS is still the task backend the table is empty and says so, rather than reading as a fault.

  It also diagnoses the configuration the Kconfig could previously only warn about. `CONFIG_REFLEX_TASK_BACKEND_REFLEX` with nothing to start the scheduler files a TCB per task and runs none of them, so the board boots, the shell answers, and every service is quietly dead. That is now one command: seven filed slots, none started, and `no slot is current — the Reflex scheduler is not running, so none of these execute`. The first version of this carried a message for "backend on, table empty" instead, which is near-unreachable — with the backend on, tasks are filed long before a shell exists to ask.

  `kernel tick`, `kernel selftest` and `kernel wdt` were never documented either, and are now in the README and user manual alongside it.

- **Task names were borrowed pointers, and at least one dangled.** `reflex_tcb_t` kept `name` as the `const char *` it was handed, and `goose_field_start_pulse` formats `"p_%.13s"` into a local `char[16]` and passes it — so the pointer died with the function. `reflex_sched_find_by_name` `strcmp`s that pointer, making this a read of a reused stack rather than a cosmetic problem. FreeRTOS's `xTaskCreate` copies the name, so the bug was latent under that backend and only bites under Reflex's own. The TCB copies into a `char[REFLEX_SCHED_NAME_MAX]` now, truncating rather than pointing. Found within a minute of `kernel tasks` existing: two slots printed garbage where they now read `p_sys.autonomy` and `p_led_agency`.

- **A retiring task left its stack allocated and its slot `DEAD`.** The self-delete path in `reflex_sched_delete_task` marked the task `DEAD` and yielded, and could not do otherwise — a task cannot free the stack it is standing on — but nothing else did it either. `find_free_slot` only reuses `FREE`, so slots did not come back, and self-delete is the normal way to retire (`reflex_vm_task_entry` ends that way). Retiring is two steps now: the task marks itself `DEAD` and yields, and `reflex_sched_reap` frees the stack and returns the slot from `pick_next`, the first point at which execution is back on the scheduler's stack and the retiring stack is provably idle. Passing a task its own pointer rather than NULL is handled as the self case instead of freeing the caller's stack, and the reap clears `started`, since a reused slot with a stale flag would send the scheduler into a `jmp_buf` belonging to a task that no longer exists. Ten host assertions, both halves mutation-checked under forced clean builds.

  **Demonstrated on hardware once the missing instrument existed.** The first version of this entry said it could not be shown on a board and listed three inert attempts as if the gap were in the hardware; the gap was that task lifecycle was not observable from outside the scheduler at all. With `kernel tasks`, the mutation is decisive: `9 of 16 in use, 0 dead` with the reap, `11 of 16 in use, 2 dead` without — `reflex-led` and `reflex-vm`, each still holding a 4 KB stack after retiring during an ordinary boot.

### Added

- **`tools/parity_check.py` and `make parity-base` / `parity-other` / `parity-diff` — the other half of the independence measurement.** The ratchet counts ESP-IDF includes removed and forbids that number from growing; it measures subtraction and cannot see whether the Reflex code that replaced a dependency still does the job. Twice it scored a replacement as progress while that replacement did nothing — the Reflex task backend could not wake a task from a delay, and the Reflex flash store persists nothing. There are three such swaps in the build, so that is two of three. This runs the same battery of shell commands against two builds and diffs them, hardware only: the host suite mocks flash as RAM, which is exactly what hid the persistence bug.

  **The result is the bedrock number for this work.** With Reflex owning the entry point, the scheduler, the trap vector and the console — the whole substrate on its own eight task slots — the system is at capability parity with the stock ESP-IDF build on every axis measured (tick 1000 Hz vs 999, LED, PWM, temperature, LP heartbeat, mesh transmit, VM programs, auth, shell) **except persistence**. One subsystem is the entire remaining functional gap.

### Fixed

- **`kernel tick` killed the machine on a build where Reflex owns the scheduler.** It calls `reflex_sched_tick_stop()`, and there that tick *is* the scheduler's clock — every task blocked forever with nothing to wake them, the board dead mid-command. Found by the parity run, where every reading after `kernel tick` came back empty and reproduced exactly. It now stops only a tick it started itself. A diagnostic that destroys the system it is diagnosing is worse than none.

- **The parity tool shipped with a check that could not fail.** `pwm_attach` read `"orient=rising" in ask(s, "bonsai exp4 status") or True` — `status` is not an exp4 subcommand, so the match always failed and the `or True` reported success regardless. Every parity run had reported PWM attach as working without testing it, inside the tool written to catch exactly that. It reads the reply to `connect` now; re-measured, the answer is genuinely true, which it had been for no reason.

- **Numeric regressions were invisible to the diff.** The verdict logic compared only booleans and `None`, so `tick_hz` could fall from 999 to 100 and print "same". Checks and observations are now declared separately: booleans plus three numeric rules (tick within 95% of baseline, no fewer VM programs, no unreclaimed task slots) get verdicts, while temperature, heartbeat, mesh counters and slot usage are context and never do — they legitimately differ between builds. Mutation-checked against a synthetic degraded run: all three fire and the exit code turns 1.

- **The parity tool left state on the device.** Its persistence probe writes a purpose and never cleared it, so on a build where persistence works the board kept it — seen afterwards as a board still reading `purpose=photography`. It cleans up now and reports whether that worked.

- **The parity tool conflated a silent command with an absent capability**, so one dead connection reported as a dozen capability regressions — which very nearly went into the record as "Reflex ownership costs everything". A run with silent commands is now marked untrustworthy as a whole rather than reported selectively.

- **The mesh version counter was counting radio noise.** `rx_version_mismatch` was checked *before* the Aura gate, so anything on the shared 802.15.4 band that happened to be `sizeof(goose_arc_packet_t)` bytes landed in it — conflating "a peer is running a different build" with "someone else's Zigbee frame", which are opposite conclusions. It sits behind the Aura gate now, exactly where the malformed check already sat and for the reason that comment gives. Measured on hardware: what had been `version_mismatch` climbing became `aura_fail` climbing, one for one.

- **Reflex's flash key-value store was writing into the `nvs` partition.** `KV_FLASH_BASE` was `0x9000` with six 4 KB sectors; `partitions.csv` puts `nvs` at `0x9000` with size `0x6000` — the same six sectors. Everything the store wrote was later overwritten by NVS, whose users include `phy_init` saving radio calibration on every boot. Avoiding the NVS *component* is not the same as avoiding NVS's *storage*. It has its own `reflexkv` partition now.

- **Its entries were written at unaligned offsets, and nothing checked.** The packed entry header is five bytes and three separate appends put the key at offset 13 and the value at 21; `esp_rom_spiflash_write` requires a word-aligned destination and its result was discarded, so the writes did not happen and reported success. Entries are now assembled whole and written once on a 4-byte boundary, `flash_write` returns a status `kv_write_entry` propagates, `esp_rom_spiflash_unlock` is called first, and a single `kv_entry_span` rule is shared by the writer and all three readers so the walk cannot disagree with the append. The host mock now refuses unaligned writes as the chip does — mutation-proven: reverting the padding fails `fill (only 1 writes)`.

- **Reflex's key-value store persists, and both Reflex configurations now reach full capability parity.** `make parity-diff` reports **zero** regressions for the independence build *and* the own-entry build against stock ESP-IDF — the two-clause acceptance test satisfied together, after four attempts that each managed one clause or neither.

  The cause was using raw `esp_rom_spiflash_*` to keep zero ESP-IDF component dependencies: raw ROM flash access while the CPU executes XIP from the same flash never reaches the medium, so a write and a read-back agreed inside one boot and the data was gone after a reset. Three real bugs were found and fixed along the way that were *not* the cause — the store writing into the `nvs` partition, unaligned unchecked entry writes, and a `Cache_Suspend_ICache` bracket that changed nothing.

  What works is `esp_flash_*` plus two things where Reflex owns the machine: `esp_flash_app_disable_os_functions` swaps the chip's own `os_func` for `esp_flash_noos_functions` — the layer `spi_flash_guard_set(&g_flash_guard_no_os_ops)` could not reach, which is why that attempt hung — and the flash calls run with interrupts masked, because the no-OS layer suspends the cache without disabling interrupts and Reflex's tick would otherwise fetch `reflex_trap_handler` from flash mid-window. The masking is conditional for the mirror-image reason: with FreeRTOS running, `esp_flash` keeps its app `os_func`, that takes a mutex, and a mutex cannot be waited on with interrupts masked — masking unconditionally deadlocked the independence build on its first write.

- **Tier F grew from 1 to 3, deliberately, and it is in the ledger.** `esp_flash.h` and `esp_flash_internal.h`. The ratchet refused the increase, correctly, and `tools/independence_baseline.json` now carries a `deliberate_increases` entry with what, why and the evidence. The store used raw ROM access *specifically* to hold that tier at 1, and that is exactly why it lost every key it was given: the count was protecting a subsystem that did not work. Independence measured as subtraction rewarded it; independence measured as capability did not.

- **The silent paths around it now speak.** ESP-IDF's NVS recovery erases every stored key on `NO_FREE_PAGES`/`NEW_VERSION_FOUND` and returned OK with no record — it logs the erase and which condition caused it (and is confirmed *not* firing here). `load_aura_key` had three ways to fall through and reported none, while falling through overwrites the operator's key with a fresh random one; it now names which step failed and with what code. `reflex_kv_init` says whether it resumed or started fresh, which is the only outward sign of the defect above.

- **Reflex's trap handler dispatches to drivers it does not own, so the peripherals come back.** Independence had been bought by switching things off: under Reflex's vector the PLIC had two live lines — the tick and the console — against nine under FreeRTOS, with `unclaimed_masked=0x00000100` recording one more masked on its first interrupt. The blob-free 802.15.4 radio transmitted and never received, reception being the half that needs an interrupt.

  Masking was right as far as it went — an unacknowledged level-triggered line stops the core — but it never asked whether anyone *else* owned the line. ESP-IDF keeps its own per-line handler table and exposes `intr_handler_get`/`intr_handler_get_arg`, so `reflex_trap_handler` now tries that before masking and masks only when nothing anywhere is registered. Declared locally rather than by including `riscv/interrupt.h`, which would have moved the independence count the wrong way for two symbols.

  Result on the own-entry build: `plic live mask` 2 lines → 3, `unclaimed_masked` `0x100` → `0`, and over fifty seconds on one connection (uptime 2.5s → 60.8s, no reset) `version_mismatch` went **1 → 7** — six frames received and parsed under Reflex's own trap vector. `REFLEX_INTR_SRC_ZB_MAC` joins the SoC bridge, now 184 constants proved against ESP-IDF.

  An adopt-the-line step was written first and deleted: it ran at hand-off, before the driver had routed its source, and reported `cpu_int=0` — the matrix reset value. A driver initialising after the quiesce enables its own line; only dispatch was missing.

- **Soaked the foreign-dispatch path, and got a control out of it.** Three minutes on the own-entry build with the radio live: heap flat at 291064 free (min_free 289012), shell responsive, `tx` 1 → 28. No leak from servicing another driver's interrupt out of Reflex's trap handler. The peer had been restored to the Wi-Fi build for that run, so `version_mismatch` stayed at **0** throughout — against 1 → 7 in fifty seconds with an 802.15.4 peer present. Frames appearing only when a peer transmits rules out stray traffic on the band, which is a better control than the two-board experiment the bench refused to run.

  Two limits now stated in the code rather than left implicit: the raw CPU line indexes ESP-IDF's handler table correctly only because the C6 is a PLIC part (`RV_EXTERNAL_INT_OFFSET` is 0 for PLIC, 16 for CLIC — the same code on a CLIC target would call the wrong driver silently), and these are ESP-IDF drivers, some of which use FreeRTOS primitives from ISR context under a scheduler that was never started. The 802.15.4 MAC survives that, measured; one driver is not a guarantee about the rest.

- **Bench constraint worth recording: two USB-serial-JTAG connections cannot be held at once**, and opening a port resets the board it is attached to. Between them those invalidate the obvious two-board radio experiment — the counters being compared are zeroed by the act of reading them, and the transmitter drops when the receiver is opened. What works is one persistent connection to the receiver, the peer left to broadcast on its own, and `status` uptime read alongside the counters to prove no reset happened mid-measurement.

- **The idle task never yielded, and that was the whole of "tasks run once and never wake from `delay_ms`".** `reflex_sched_init` always creates an idle task at priority 0, and its body was `while (1) { wfi; }`. So the first task to block ended the system: the scheduler picked idle, idle never came back, `pick_next` never ran again — and the sweep that wakes timed sleepers lives inside `pick_next`. Because idle is always READY, `pick_next` also never returned NULL, so the scheduler's own idle path was dead code, which is why a probe placed there printed nothing. A probe on the scheduling decision itself printed exactly once per boot.

  Every part of the waking machinery was correct and unreachable: the tick at 1000 Hz under Reflex's own vector, `s_tick_count` volatile, `reflex_sched_should_time_wake` and its host tests, the sweep itself. The fix is the missing `reflex_sched_yield()` after the `wfi`.

- **Reflex OS boots and runs entirely on its own kernel.** With `make own-entry-build`, the entry point, scheduler, trap vector and console are all Reflex's, FreeRTOS is never started, and the shell answers commands — `kernel tick` reports 1000 Hz with two PLIC lines live, the tick and the console. `system_stable=confirmed` is the proof that matters: it is published by a task that first sleeps for seconds, so it can only appear if a timed wake fired.

  `kernel selftest` corroborates from the ordinary build, where it had run each task once and stopped. Both cooperative tasks now run to completion at their configured periods: task A every 100 ticks, task B every 130.

- **The post-install tick check stranded the board where the pre-install one recovers.** It stalled on `wfi`, which needs a reflash to leave, while the earlier check hands back and keeps a working system — the same shape as the sleep watchdog whose own failure mode was the thing it existed to prevent. Found by the mutation above failing to fail. It is a fast path now and is described as one.

- **The own-entry configuration had no build recipe.** It was assembled by hand into a scratch file outside the repository, so the one build that demonstrates Reflex keeping the machine was the one build nobody could reproduce — and it did not survive a restart. `sdkconfig.defaults.own_entry` and `make own-entry-build` close that, exactly as `sdkconfig.defaults.independence` closed the same gap one layer down.

- **`REFLEX_OWN_ENTRY` refuses to build without `CONFIG_REFLEX_TASK_BACKEND_REFLEX`.** The two options are independent in Kconfig and nothing paired them, so the wrong combination ran `app_main` on the Reflex scheduler while it created its tasks on a FreeRTOS that was never started — not a link error and not a crash, but a boot that stops partway with no explanation. Checked in both directions: refused without it, builds with it.

- **The entry path verifies the tick a second time, after taking `mtvec`.** The existing check proves the tick under ESP-IDF's trap vector and says nothing about it under Reflex's — and installing the vector is exactly the step that could break it, while a scheduler with a stopped clock does not crash, it parks on `wfi` and goes quiet. It reports **50 ticks in 50 ms**, so the handover is clean, and that is now a permanent guard rather than an assumption.

- **Reflex's trap handler was not an interrupt dispatcher, and that read as a hang.** It serviced the scheduler tick and deliberately left every other line alone — right while it only ran for the length of `kernel selftest`, wrong once Reflex owns the entry point and is the machine's only dispatcher. "Leave it alone" is not what happens to a level-triggered line: an unacknowledged one re-enters the instant the handler returns, forever, so the choice was never *leave it alone*, it was *stop the machine*. ESP-IDF allocates interrupts of its own during boot (the radio, the LP timer) that are invisible to Reflex's table, and the first to fire after `mtvec` was taken locked the core — no output, no fault, and a stop point that moved with when it arrived. - **`build_*/` is ignored.** `.gitignore` covered `build/` and not the out-of-tree configuration directories, so a `git add -A` committed 4906 build artifacts from `build_own_entry` across three commits. Ignored and untracked now; the objects remain in history.

- **The tick interrupt was enabled at the wrong bit of the `mie` CSR, and the default build has never delivered it.** `reflex_hal_intr_alloc` set bit `16 + cpu_int` — the ESP32-C3 mapping. On the C6 the bit is `cpu_int`, so for the scheduler tick on line 11 it was enabling **line 27, one of Wi-Fi's**, and never line 11.

  It hid for as long as it did because it only matters when nobody else has already enabled the line. Two builds differing in nothing but the radio, every PLIC register identical — enable, priority, threshold, type — and one source routed to the line: `mie=0x0f000f24` (bit 11 set) gave 998 Hz on the 802.15.4 build, `mie=0x0f000726` (bit 11 clear) gave 0 Hz on the Wi-Fi build with the source asserting in 1000 of 1000 samples. In the first, ESP-IDF had already claimed line 11 for source 12 and set the bit, and Reflex inherited it. The console had been surviving the same bug the same way, on a line ESP-IDF enabled first — so the standing note that "CPU interrupt 10 is verified safe on C6" was true for the wrong reason.

The console ISR-entry counter was the control that made the answer findable: a responsive shell does not prove its interrupt is delivered, because it could be polling.

- **Reflex now keeps the machine.** With that fixed, `REFLEX_OWN_ENTRY` on the independence configuration no longer falls back: the tick passes its own check, the hand-off runs, `mtvec` is taken, and `app_main` runs on the Reflex scheduler with FreeRTOS never started — `main_task: Started on CPU0` is absent from the log. Reached rather than forecast now. `REFLEX_OWN_ENTRY` stays off by default until the shell survives it.

### Changed

  Also noted: the `mie`/`mip` fields in that readback use the C3-style `16 + cpu_int` mapping, and ESP-IDF's PLIC path never touches `mie` for external interrupts. Those two bits are probably reporting nothing meaningful on the C6, so `mip=0` is not evidence that the core never saw the interrupt.

- **The LEDC leak was fixed on one target and left on the other.** `bonsai exp4 detach` gives the PWM peripheral back, but the release was written inside `#if CONFIG_IDF_TARGET_ESP32C6` while the command runs on both boards — so the classic ESP32 kept the identical defect the fix was written to remove, re-routing the pin while ESP-IDF's LEDC stayed configured and clocked. It now releases on both: `reflex_hal_pwm_release()` on the C6, `ledc_stop()` on the ESP32.

  Register evidence on the C6, read back through `goonies read agency.ledc.ch0_conf0`: `0x00000000` before any attach, `0x00000004` (`SIG_OUT_EN`) after `connect`, `0x00000010` after `detach` — the enable bit genuinely cleared, and the clock-gated peripheral still reads back without stalling, so the probe path is safe after a release.

- **`ledc_stop` was only half the release on the classic ESP32.** `ledc_channel_config` also takes an `esp_gpio_reserve` on the LED pin's output path, and `ledc_stop` does not give it back. The board reported it: a second `connect` after a `detach` printed `W (6086) ledc: GPIO 2 is not usable, maybe conflict with others` — LEDC finding its own stale reservation from the first attach. `detach` now calls `esp_gpio_revoke` too, and three full connect/detach cycles run clean. ESP-IDF's own reservation bookkeeping is a better witness to a complete release than any print of ours.

- **`bonsai exp4 detach` configured LEDC so that it could immediately release it.** From a cold boot `ledc_initialized` is false, so `detach` fell into the init path first — harmless while detach did nothing, a configure-then-stop round trip once it released. Cold detach now re-routes the pin and returns. The readback had to be skipped with it: the snapshot reads LEDC registers and was only safe there because init had ungated the peripheral.

- **The exp4 readback printed five zeros on the classic ESP32 and called them registers.** `reflex_hal_pwm_snapshot` is a stub there — it zeroes the struct and returns — so the line that exists to report what the peripheral actually latched showed `timer=0x00000000 ch0=0x00000000 ...`, indistinguishable from a correct readback of a dead peripheral. A readback incapable of failing is worse than none. It now says `readback=unavailable (no snapshot on this target)`.

- **The trap vector was never installed where the code believed it was.** `mtvec` was written with the handler's address on the assumption of direct mode and 4-byte alignment. Reading the CSR back showed `0x4201d901` where `reflex_trap_entry` was at `0x4201d9b0`: the hardware **masks the base to 256-byte alignment** and **forces vectored mode** (ESP-IDF's own `mtvec` reads `0x40800001`). So the vector landed `0xb0` bytes before the handler, and interrupts dispatched to `base + 4*cause` — into whatever instructions happened to precede it.

  That is why the scheduler could run two cooperative tasks and then die on the first tick. Nothing about the stack switch was wrong; the trap never arrived where it was aimed. There is a real vector table now — 256-byte aligned, in IRAM, 32 entries each jumping to the common handler — and `mtvec` reads back `0x40803101`, exactly the table. The tick counter advances across tasks (`sys=2`, `sys=3`) where it was previously stuck at 1.

  Two more defects were caught building it, either of which would have produced another silent wrong-target: the assembler **compressed each `j` to a two-byte `c.j`**, giving a 64-byte table where vectored dispatch needs 4-byte entries, so cause 11 would have reached entry 22; and the exit path re-established `mscratch` by loading a pointer *variable* that the linker had placed **in flash** at `0x420f2828` — a flash read on every trap return, from inside the trap handler. The address is materialised with `la` now, no memory access on the trap path.

- **The handler and its vector table moved to IRAM.** A trap handler in flash cannot run while the cache is disabled, which is exactly when a trap is least affordable.

- **`kernel selftest` measures the tick before handing over.** On the default build the tick is 0/5 with the routing reading back perfect, so taking `mtvec` there quiesced FreeRTOS, gave the core to a scheduler that could never unblock a task, and left a board needing a reflash — for a reason unrelated to what was being tested. It now samples the tick over 50 ms on the same path the scheduler will use and refuses the hand-off if it is dead. Verified on that build: `ABORT: tick is not running (0 over 50ms)`, and the shell comes back.

- **`mscratch` was never initialised, and never re-established on trap exit.** The vector's first instruction is `csrrw sp, mscratch, sp`, so the 132-byte frame is written wherever that register happens to point — and since entry leaves the interrupted `sp` there, a second trap would build its frame on the task's own stack, on top of whatever the task was doing. Both halves fixed: a trap stack in `.bss` with `mscratch` set before `mtvec`, and the exit path putting it back.

  **With an anomaly that is not resolved.** Left uninitialised, the hand-off got *further* — the two task lines above are from that build. Set correctly, it dies at the `mtvec` install itself, consistently across three runs. A vector that swaps an uninitialised register into `sp` cannot be correct, so the fix is right on its face, and the board disagrees. It is kept as the fix and recorded as unexplained rather than reverted to the luckier version, because "correct by reasoning, worse by measurement" is the exact shape of the mistakes this work keeps finding. That is where C3 resumes.

  Nothing that ships is affected: `kernel selftest` is admin-gated, nothing calls it, and normal operation is untouched.

- **`kernel selftest` starts the Reflex scheduler, and it gets further than the plan implied.** Nothing had ever called `reflex_sched_start`, so "does the scheduler work" had never been asked of hardware. It is now, from an admin-gated shell command that hands the calling task to the scheduler and does not give it back. On the independence build, where the tick runs at 1000 Hz, the scheduler **starts, picks a task, and reaches the first stack switch**.

  There it panics: `Guru Meditation Error: Core 0 panic'ed (Stack protection fault). Stack pointer: 0x408369b0   Stack bounds: 0x40825c28 - 0x40827e20`. The switch is not obviously wrong — that SP is inside the Reflex task's own stack. ESP-IDF arms a stack-pointer watchpoint with the bounds of whichever FreeRTOS task is running, and does not know Reflex's stacks exist.

- **`reflex_hal_stack_guard_disable`** releases that watchpoint (constants through the bridge, 175 -> 178; IDF calls the register `INTR_ENA` where the SVD says `MONTR_ENA`). **It does not fix the panic, and that is the finding.** FreeRTOS re-arms the watchpoint on every context switch and its tick is still running, so the two schedulers cannot coexist even for the length of one experiment.

  **So the `mtvec` hand-off is not a third blocker queued behind the other two — it is the problem.** Until Reflex owns the trap vector and FreeRTOS is quiesced, the first stack switch keeps being undone by the system it is replacing. That is a much sharper statement of C3's remaining distance than "three things are missing", and it came from running it rather than reading it.

- **The self-test no longer allocates the tick itself.** It routed SYSTIMER_TARGET1 and then called `reflex_sched_start`, which routes and arms it too — two allocations of one source, landing on different CPU lines. Harmless only because nothing ever called it.

- **A recovery net for deep sleep, proved rather than assumed — and it does not yet work where it is needed.** Owning the sleep entry is the one dependency whose failure mode is silent and unrecoverable: get it wrong and the board never wakes, with nothing left running to say why. The mitigation is the low-power watchdog, which lives in the always-on domain: armed before sleeping, it turns "never wakes" into "reboots a few seconds later". `reflex_hal_wdt_arm/feed/disarm/armed/regs` own it directly, constants through the SoC bridge (161 -> 175). `kernel wdt <ms|off>` arms it, gated at `admin` because it is a reboot by another name.

  **Awake, it works: armed for 5000 ms, the board reset on schedule.** It did not on the first attempt, and the reason is worth recording — the configuration read back exactly as intended, `WDT_EN` set, stage action `RESET_RTC`, the timeout correct to the tick, and nothing happened. Both reset-signal length fields were zero, which is a 100 ns pulse that does not take. ESP-IDF sets 3.2 µs. *Armed is not the same as working*, and only reading the register back showed the difference.

  **Across ESP-IDF's deep sleep, it does not fire — and that is unexplained.** Armed for 5 s and asked to sleep 30, the board returned at 33.6 s on its own timer. `WDT_PAUSE_IN_SLP` was clear at arm time, and ESP-IDF's own sleep path says in as many words that a watchdog enabled by user code is left alone. The source and the measurement disagree, and rather than pick one, this is recorded as measured and not understood. It matters because the whole plan for owning sleep rests on this net, and it is not yet trustworthy where it counts.

- **The watchdog is disarmed on boot**, which is not a detail. It survives the reset it causes, so arming it and letting it fire brings the board back with it still armed, and it fires again. That reset loop is not hypothetical: it happened during this work, and the hardware suite recorded it exactly — 73 checks, then 0, then 0. ESP-IDF's bootloader arms this watchdog and its app startup disarms it for the same reason. A recovery net that bricks the board it exists to recover is worse than none.

It presents as a console with **no output at all** — which reads as a transmit fault and is not one. Found by disabling the receive interrupt and changing nothing else: full boot log off, not one byte on.
  - The acknowledgement came after the drain, so a packet arriving mid-drain was acknowledged while its bytes were still in the FIFO. Nothing remained to announce them. The console worked, then stopped permanently, 86 checks in.
  - The transmit bound was 20000 spins — well under the 1 ms frame on which the host services the endpoint, so a host that had not just polled lost the rest of the line. It showed as replies desynchronising from prompts with echoes cut mid-word, which is not corruption: every byte present, spread across more reads than the caller expected.
  - Its replacement read the standard RISC-V cycle CSR, which reads back as **zero** on this part — `SOC_CPU_HAS_CSR_PC` moves the counter to a vendor CSR. A zero clock never expires a deadline, so the first write with no reader spun forever and the board stopped enumerating, presenting to the host as absent rather than busy. That firmware had to be flashed out blind. It now uses `reflex_hal_time_us`, already in the same file, already reading SYSTIMER unit 0; `reflex_hal_cpu_cycles` twenty lines below had been reading the correct vendor CSR all along.
  - ESP-IDF's console completes a packet only on a newline, and `reflex> ` has none — so `fflush` was not enough and the prompt sat in the FIFO until the *next* command's echo flushed it. Every reply looked one behind. Measured directly: a command returned its full text and its outcome marker, then nothing for eight seconds, and the missing prompt turned up prefixed to the following command.
  - Writing directly at the endpoint took the shell's output out of the lock keeping it apart from the supervisor task's logging. Both write the same FIFO; a log line landed inside a reply. Three failures in ten runs where main had none in five. The direct writes now hold `flockfile(stdout)` — the lock `printf` already takes — rather than inventing a second one.

- **A seventh fault, visible only at ten runs: a reply missing its first character.** ESP-IDF's console still emits the shell's command output, and its write path pushes its first byte without checking `IN_EP_DATA_FREE` — so if our packet handover was still in flight, that byte was lost. One occurrence in sixty runs of the same command sequence, surfacing as a usage line reading `apestry signal <cell>`. `usj_write_bytes` now waits for the endpoint to accept bytes again after `WR_DONE`; the wait is not for us but for whoever writes next, which is the cost of sharing an endpoint Reflex no longer exclusively owns. Zero in sixty after, and the suite went from eleven of twelve to twelve of twelve.

- **The SYSTIMER counter registers moved behind the SoC bridge** (57 -> 61 constants, all proved identical to ESP-IDF). They were hand-written offsets in the HAL, which is exactly the class of constant the zero-clock bug came from; `reflex_hal_time_us`'s own base address had been wrong once before in the same way.

- **`-DREFLEX_CONSOLE_RX_DIAG=1`** — a board that has stopped answering can still be asked a question, over transmit, which is the half that usually still works. It reports whether the receive handler ran, how many bytes it buffered, and whether anything consumed them, separating three failures that look identical from the host. It is what ended four rounds of reasoning about the wrong half of the console, and it is documented in `CONTRIBUTING.md`.

### Fixed

- **A check that drew a confident conclusion from the wrong build.** The first version of the image cross-check reported `reflex_radio_802154.c`'s ESP-IDF include as discarded dead code. It is not: the include scan measures the independence configuration (C6 with the 802.15.4 radio) while the linker map is whatever was last built, and that build has no radio. "Absent from the image" has two causes and the check could not tell them apart — it simply asserted the interesting one. It now reads `sdkconfig` first and draws the conclusion only when the map is the configuration being measured, saying so plainly otherwise. Verifying the independence build itself is the outstanding follow-up.

- **A comment that said the pin was handed back, over code that did not.** `reflex_hal_rmt_release` stopped the channel and gated the clock but left the pin routed to the transmit signal with its input buffer forced on for the rest of the boot — the same debt the counter had one commit earlier, in the function written immediately after fixing it. A comment asserting the work was done is worse than no comment, because it is what a reader checks instead of the code. It now detaches the signal, returns the pin to an input, and says only what it does.

- **A resolution the divider could not produce exactly was silently rounded.** `reflex_hal_rmt_tx_init` divided and truncated, so a caller asking for 3 MHz would have got 3.077 with no indication — the same shape of quiet wrongness as a duty cycle computed against the wrong crystal. Inexact resolutions are refused now.

- **A bare `128` in `shell.c`** meaning "route the pin back to plain GPIO" is `REFLEX_SIG_GPIO_OUT_IDX`, through the SoC bridge like every other signal index.

- **A preprocessor guard evaluating an undefined macro.** `shell.c` fenced its console on `SOC_USB_SERIAL_JTAG_SUPPORTED`, which reads correctly only once `soc_caps.h` has been included — and this file was receiving that transitively through `driver/rmt_tx.h`. Removing that include as part of owning RMT left the first `#if` evaluating an undefined name: it took the else branch, pulled in `driver/uart.h`, and `uart.h` then defined the macro so every later guard evaluated the other way. The build worked, by accident of include order, while quietly reacquiring two includes Tier E had already shed. The independence checker's build-agreement test caught it — the tool claimed Tier E was clear while the compiler's dependency list disagreed, which is the disagreement that test exists to surface. The fence is `CONFIG_IDF_TARGET_ESP32C6` now, which comes from `sdkconfig.h` and is force-included into every source file, so it cannot be undefined where it is used.

- **PCNT was released by pausing it, which gives nothing back.** Both pins stayed routed into the counter's matrix inputs and the peripheral stayed ungated for the rest of the boot — the same "side effect the caller did not ask for" already fixed for GPIO 6 a commit earlier, missed one function over. `reflex_hal_pcnt_release` now pauses, holds the unit in reset, routes the constant-zero source into both signal indices (which is how the matrix disconnects an input, and what ESP-IDF's own `del_unit` does) and gates the clock back off. The five-consecutive-runs check is what proves it: releasing has to leave the peripheral re-acquirable, and that check fails if it does not.

- **A hardware check that vanished instead of skipping.** The PCNT comparison was guarded by a bare `if`, so on a target that does not run the experiment it reported nothing at all — indistinguishable from having passed. The LEDC comparison beside it already used the counted `SKIP`, which exists precisely so coverage cannot go quiet. The classic ESP32 now reports three named skips rather than two and a silence.

- **A constant nothing read.** `REFLEX_PCNT_CTRL_CLK_EN` was generated and never used; the unused `LEDC_CONF` entries were dropped for that reason a commit earlier and this one slipped through the same gap.

- **A clock that could jump 268 seconds forward.** `reflex_hal_time_us` triggers the SYSTIMER value latch and then reads LO and HI as two separate registers, with nothing making that indivisible. There is one latch shared by every caller and this function has many across several tasks, so a caller preempted between the two reads has the sample replaced underneath it and gets its halves from different instants. Almost always harmless — the counter is monotonic, so a mixed sample is merely slightly late — but not when LO has just wrapped: HI is then one greater than the LO it is paired with and the result lands 2^32 ticks ahead, which at 16 MHz is 268 seconds. That clock backs `LOOM_LOCK_TIMEOUT_US`, all of 300 microseconds, so the visible failure is a spurious `LOOM_CONTENTION_FAULT` on a lock held for no time at all, with uptime, telemetry ages and peer timeouts inheriting the same jump. The window is two instructions wide and needs a wrap to coincide with it, which is why it has never been seen — and the console transmit path now calls this on every byte it waits for, so the odds stopped being negligible. The latch and both reads are now one critical section, restoring the previous interrupt state rather than unconditionally enabling, because callers inside the loom hold already have interrupts off. Loom timing unchanged on hardware afterwards: `max_us` 328 against the 324-333 already on record, `avg_us` 6.

- **The independence measurement was counting dependencies the independence build does not have.** `tools/check_independence.py` scanned every `#include` in a file regardless of whether the C6 actually compiles it. `shell/shell.c` fences `driver/uart.h` and `driver/uart_vfs.h` behind `#if SOC_USB_SERIAL_JTAG_SUPPORTED ... #else`, so that build has never included either — confirmed against its own dependency output — while the tool put Tier E two higher than it was. Since this file is the declared single source of truth for independence status, an overestimate is not a safe error: it misreports the thing everything else is measured against. The scanner now tracks `#if`/`#ifdef`/`#ifndef`/`#elif`/`#else`/`#endif` and skips branches the independence path cannot take, treating any condition it does not recognise as taken so an unrecognised guard can never hide a real dependency. **Tier E 6 -> 4, on-path total 21 -> 19**, with no code change — the four that remain are `ledc`, `pulse_cnt`, `rmt_tx` and `rmt_encoder`, which is exactly what the compiler reports.

- **`make independence-test`** — the checker's new parser is tested, including against the C6 build's dependency output, which is the only authority on what was actually included. Mutation-checked: restoring the old scan fails four of them. A parser inside the tool that defines every tier number, with nothing exercising it, is a measurement nobody has checked.

- **A shell command could reboot the board.** `bonsai exp5 run` hardcodes GPIO 4 and GPIO 6, and on the classic ESP32 GPIO 6 is one of the pins wired to the SPI flash — configuring it as an output cuts the chip off from the code it is executing and the watchdog resets it (`rst:0x8 (TG1WDT_SYS_RESET)`). Reproduced on that board with this build *and* with main's, so it is long-standing rather than new; it surfaced because the hardware suite started exercising the command. "No command can wedge the board" is one of the acceptance criteria in `docs/adoption-gaps.md`. The experiment now says it is not wired for the target and stops.

- **`bonsai exp4` had never once driven the LED, and said otherwise every time.** It configured the LEDC channel with `gpio_num = -1`, intending to attach the signal by hand afterwards — a reasonable technique that LEDC rejects outright (`ledc_channel_config(844): gpio_num argument is invalid`). Nothing checked the return, so the handler printed the orientation it had not applied and reported `#R:+1,ok`. The channel is now bound to the LED pin, both configuration calls are checked, and a failure is reported as one.

- **`bonsai exp5 run` leaked a PCNT unit on every run.** `pcnt_del_channel` was never called, so `pcnt_del_unit` failed with "channel 0 still in working" and the unit was never returned. The C6 has four; the fifth run would have failed for a reason with nothing to do with the experiment. It also read its counter after a fixed 100 ms delay rather than after the transmission it was measuring, so the count was whatever that interval happened to catch — `rmt_tx_wait_all_done` replaces it. The encoder is freed too.

- **Every unmatched `bonsai` subcommand reported success.** A wrong verb, or a verb whose second word matched nothing, fell off the end of the dispatcher and returned `#R:+1,ok` having done nothing: `bonsai nosuchthing`, `bonsai exp4 bogus`, and `bonsai exp5` without `run` — the last being the easy mistake, because every other experiment takes `start`. All now print usage and return `#R:0,usage`.

- **The same leak was still on the error path.** Fixing `bonsai exp5`'s success path left `rmt_new_tx_channel`'s failure path calling `pcnt_del_unit` with the channel still attached — failing and leaking the unit exactly as before. Three hand-written unwind paths is why the bug existed in the first place, so there is now one: every acquisition records what it took, every exit runs the same cleanup, and each step's return value is checked and named if it fails. GPIO 6 is handed back with `gpio_reset_pin` too, because leaving a pin driven is a side effect the caller did not ask for and `make hw-test` now runs this five times.

- **Seven hardware checks cover the above**, including five consecutive `bonsai exp5 run` invocations, which is what a leaked unit actually looks like from outside, and an exp4 connect/detach round-trip that drives the LED both ways afterwards — a pin stuck at one level would satisfy a single read. Mutation-checked individually: reverting the dispatcher, the missing `pcnt_del_channel`, or exp4's pin binding each fails the check that covers it. The first attempt at that last mutation silently did not apply, because clang-format had respaced the initialiser it was matching on, and a mutation that does not mutate proves nothing — the retry asserts the edit landed before building.

- **Two more checks that asserted the board stayed silent.** The supervisor emits telemetry on its own schedule, so `I (GOOSE_SUPERVISOR) snapshot saved` can land between a command's write and its echo. The suite mishandled that twice: it stripped the echo only when the echo came first, so an async line ahead of it left the command text in the response and checks began reading the command back instead of the answer; and several checks compare for exact equality — a denial must be the *whole* answer, so nothing leaks past the guard — which additionally asserted the board said nothing else meanwhile. The strictness is kept: the echo is now identified by content rather than position, and lines the board emits on its own schedule are filtered before comparison. Owning transmit is what made this visible — ESP-IDF's buffered driver placed async output at different moments, so the suite had been passing on a timing accident rather than on a property. Re-run five times against main's firmware.

- **A hardware check that asserted something the system never promised.** `sys cell unchanged` sampled `sys.kernel.disposition` before and after a refused signal — but the supervisor rewrites that cell on every policy pass from live counts, so the comparison was racy by construction, and worse than it looked: it sampled the cell again for its label and a third time for the comparison, comparing the first read against the third with two command round-trips in between. It passed by being lucky about timing, and any change that shifted timing could unmask it without breaking anything. Now a trial counts only when the cell reads the same either side of a control round-trip, and skips with a reason if the supervisor is active throughout. Verified against main's firmware as well as the branch's, so it is sound rather than merely accommodating.

- **The USB-serial-JTAG register constants are Reflex's own** — the header goes from 47 to 57, each derived from the SVD and `_Static_assert`ed against the ESP-IDF macro it replaces. The SVD calls this peripheral `USB_DEVICE` where IDF calls it `USB_SERIAL_JTAG`; recording that divergence is precisely what the scraper's mapping table exists for. The C6 HAL's hand-written `USJ_BASE + 0x00 / + 0x04` literals now come from the generated header, so they are covered by `make soc-bridge` rather than being a second transcription of the same register map that nothing can check — the same duplication just removed from the shell. Console verified unaffected on hardware: 171/171 on both C6 builds after re-pointing its TX addresses.
- **Tier E's remaining work is designed rather than described.** "RX needs a queue primitive" understated it: the queue is necessary and not sufficient. The ESP-IDF driver owns the OUT-endpoint FIFO once installed, so direct reads race it and owning RX means not installing it; polling cannot replace it because the shell idles 50ms while a 64-byte FIFO fills in 5.5ms at 115200 baud — which is not a prediction but what the CHANGELOG records happening before the driver was installed; so RX must be interrupt-driven into a ring, now possible because `reflex_hal_intr_alloc` works on the path the tick is measured on. Source 48, `SERIAL_OUT_RECV_PKT`. (Written here as 39; `make soc-bridge` caught it.) And `printf` reaches the wire through the VFS driver rather than `reflex_hal_write_raw`, so stdio must move at the same time — which is why the Tier E include count does not fall until both halves land.

- **`make tick-measure` / `tools/measure_tick.py`** — the Reflex scheduler tick is measured across repeated cold starts rather than characterised from single samples, which had been wrong three times running. Each cold start is performed with the shell's own `reboot` and then **verified** by reading uptime back; a run whose coldness cannot be confirmed is reported, not counted. That verification is the point: the first version of this script assumed that opening a C6's USB-JTAG port resets the board, and it does not — six consecutive opens read uptime 925.9, 934.5, 943.1, 951.7, 960.4, 969.0 seconds, monotonic. Every "cold start" it measured was really a re-arming on a continuously running board, and the 1-of-8 baseline it produced was an artifact of that.
- **With cold starts actually cold, the tick works: 5/5 and 6/6 at 1000-1001 Hz against a 1000 Hz target.** The three ordering and bit fixes hold, the 16 MHz period derivation is right, and the earlier retraction of "the tick works" is itself withdrawn — it works on a cold start, every time.
- **The real defect is re-arming, now precisely isolated.** On one boot: arming 1 gives 1001 Hz, armings 2 through 5 give one tick, one tick, one tick, zero. The routing readback on a failing re-arm is *identical* to the working case — same CPU line, PLIC enabled, `mie` and `mstatus.MIE` set — with the SYSTIMER source asserting and latched (`raw=0x2 st=0x2`). Everything correct, nothing delivered. Four hypotheses were tested on hardware and all four rejected: PLIC-aware line allocation (broke the working case outright), threshold-derived priority, reordering the arming sequence (dropped a working arming to one tick), and clearing the PLIC pending bit. The free-path pending clear was kept because handing back an asserting line is wrong on its own merits — `PLIC_MXINT_CLEAR` was defined in that file and written by nothing — but it explains nothing here.

- **`make independence` / `make independence-check` — the independence status is now measured, not remembered.** `docs/independence-dependency-map.md` is declared the single source of truth and had drifted three ways: Tier A1 claimed 52 owned register constants where the generated header and its 47 `_Static_assert`s both say 47; Tier E's status read "RX needs a queue primitive" when C1 had already built that queue (`kernel/reflex_kqueue.c`), leaving E unblocked-but-unstarted rather than blocked; and section 6 said "no hardware was attached for any of this", contradicted by section 5's own on-hardware tick work. All three corrected in place. `tools/check_independence.py` classifies every remaining ESP-IDF include by tier and enforces two things in CI: no tier may grow (independence moves one way), and an include it cannot classify is an error rather than a warning, so a genuinely new kind of coupling cannot arrive disguised as noise. Verified to exit non-zero on both. Measured at `641263b`: **23 on-path** (Tier A clear; B 2, C 8, D 1, E 8, F 4) plus 19 off-path that are deliberately borrowed and reported but not ratcheted, so "off-path" stays a decision rather than a hiding place. `prd-full-independence.md` and `v3-independence-plan.md` now carry a banner pointing at the measurement; they remain the record of the plan, not of its status. The two tier schemes are also disentangled at the top of the map — the v3 plan's A/B/C is the abstraction migration and is essentially complete, while the map's A1-F asks the harder scaffolding question.

- **A Reflex-routed scheduler tick** (`reflex_sched_tick_start` / `_stop`, `kernel tick`) — the piece C2 said was missing turned out to be already written and unused: `reflex_hal_intr_alloc` does the interrupt-matrix mapping, the PLIC priority and the `mie` bit, and registers through the ROM vector table, so it coexists with ESP-IDF's `mtvec` and needs no takeover. Nothing called it. The tick now routes SYSTIMER TARGET1 through Reflex's own plumbing rather than `esp_intr_alloc`, which is the distinction C2 was about. Written and routed but **not yet proven to fire** — see the boot panic below.

- **Hardware validation on two XIAO ESP32-C6 boards.** `make hw-test` passes **171/171**, which executes for the first time every contract case this audit added and could not run: `goonies read agency.io_mux.date` returns `#R:-1,guard` (the Sanctuary Guard fix, live), the `mesh peer add` separator and over-long-name rejections both return `#R:-1,invalid`, and bare `snapshot`/`purpose` return `#R:0,usage`. Both boards discover each other over the mesh (`peers=1`).
- **The loom telemetry fix is measured, not argued.** Flashed with the fix and with the defect deliberately reintroduced, `telemetry on`, one `bonsai bloat` burst (161 evictions, fabric saturated): the defect held the loom for **13,877 µs** peak and **383 µs** average against a `LOOM_LOCK_TIMEOUT_US` of 300; the fix gives 3,363 µs peak and **16 µs** average — **24× better on average**. The original framing needed correcting, though: `usj_write_bytes` spins only when the FIFO is full, so with a host actively draining the port the *defective* build measures 635 µs, indistinguishable from the fix. The cost is conditional on the reader, which is worse rather than better — it appears when the Loom Viewer is slow, disconnected or paused, and disappears the moment anyone attaches a terminal to look.

- **A task backend with no FreeRTOS** (`kernel/reflex_task_reflex.c`, `CONFIG_REFLEX_TASK_BACKEND_REFLEX`) — all thirteen functions of `reflex_task.h` implemented on `reflex_sched_*` and `reflex_kqueue_*`, compiling against nothing but Reflex's own headers. The whole firmware links with it selected, which is the milestone: the interface the substrate and VM use for every bit of concurrency can be satisfied entirely by Reflex code. It needed three additions to the scheduler first — `reflex_sched_find_index`, `set_priority` and `get_priority` — and the lookup skips FREE and DEAD slots, because a slot keeps its name pointer after the task is gone and would otherwise resolve a name to a corpse. **Default n, and it must stay off:** nothing calls `reflex_sched_start`, verified by `nm` on a build with the option set — `reflex_sched_create_task` is linked and `reflex_sched_start` is not — so `reflex_task_create` files a TCB into the table and no task ever runs. A board with this enabled boots ESP-IDF, creates tasks that never execute, and does nothing. Selectable so the remaining work is a Kconfig flip rather than a rewrite.

- **The scheduler's task selection is tested** (`reflex_sched_select`) — which task runs next was the least examined decision in the kernel, because it lived inside `pick_next` and `pick_next` is not compiled on the host. Extracted and pinned: highest priority wins, ties broken by a scan starting after the current task, which is what makes equal priorities round-robin instead of always returning the lowest slot. Fifteen assertions and four mutations, one of which is only caught by a negative start index.

- **The Reflex scheduler has a queue** (`kernel/reflex_kqueue.c`, `kernel/reflex_kqueue.h`) — the one primitive `reflex_sched.h` was missing, and the reason `reflex_task_kernel.c` still delegates to FreeRTOS. The ring is fixed-capacity, allocation-free after creation, and deliberately free of any scheduler dependency, so the part where ring buffers actually fail is testable on a host: wraparound, and the `head == tail` ambiguity that reads as both empty and full. `reflex_sched.c` adds blocking send and receive on top, parking a caller until a peer acts or a deadline passes. Verified against a reference FIFO over 20,000 randomised operations compared after every step — a ring that diverges and re-converges would pass a final-state check — and proved by seven mutations, all caught. Host suite 355 -> 401 tests. Named `reflex_kqueue_*` because `reflex_task.h` already declares `reflex_queue_create` with a different return type, which would be a one-definition-rule violation once both landed in one image.

- **`docs/independence-dependency-map.md`** — what ESP-IDF is actually required for, measured from link maps and `nm` over two real builds rather than from `#include` lists, and the order those needs can be retired. It corrects the standing assumption in `reflex_task_kernel.c` that FreeRTOS must stay because ESP-IDF drivers spawn tasks: in the 802.15.4 build the **entire radio stack creates no tasks at all**, the console driver needs queues rather than tasks, and the only task-creating archives besides FreeRTOS itself and Reflex's own are `esp_timer` and `pthread` — both pulled in by newlib, which makes FreeRTOS's final removal a C-runtime problem rather than a radio one.
- **The standalone-scheduler path is compiled** (`platform/esp32c6/CMakeLists.txt`). `reflex_startup.c`, `reflex_trap.c` and `reflex_vectors.S` were in no CMakeLists at all and had never been through a compiler; `reflex_sched.c` was compiled but discarded by the linker, so `CONFIG_REFLEX_KERNEL_SCHEDULER=y` produced an image containing no Reflex scheduler. All four are now built in that configuration and all four compile clean at `-Wall -Wextra` with the real toolchain. They remain unreferenced and the linker still discards them: no symbol from any of them appears in the linked image, verified with `nm`. The image is not byte-identical and cannot be — building one configuration twice from identical sources produces different bytes, so ESP-IDF's build is not reproducible here — and building with and without them differs by 8 bytes of `.flash.rodata` layout padding with no symbol changing size. The measurable claim is that no code from these files reaches the image. The point is that the scheduler can no longer rot silently while the work to reach it is still ahead, which is the position `goose_weave_loom` was in when its hardening turned out to have been verified by inspection only.

- **Reflex owns its SoC register constants and ROM entry points** (`include/reflex_soc_esp32c6.h`, `include/reflex_regops.h`, `include/reflex_rom_esp32c6.h`). Reflex reached into ESP-IDF's `soc` register headers for 52 constants and its `esp_rom` headers for 14 declarations, and none of it was ESP-IDF code: register addresses and bit positions are silicon facts, volatile load/store macros are something the compiler already knows, and the ROM routines are burned into the chip. All 46 register constants are now **generated from `tools/esp32c6.svd`** — the vendor file already backing the 12,738-node shadow atlas — by `tools/soc_scraper.py`, and none were transcribed by hand, because a mistyped register address does not fail to build, it writes to a different peripheral. `make soc-bridge` proves every one identical to the ESP-IDF macro it replaces by compiling a translation unit of `_Static_assert`s with the real toolchain; `make rom-check` verifies every ROM address against ESP-IDF's own `esp32c6.rom.ld`, following its aliases. Boot0 goes from eleven ESP-IDF register headers to none, keeping only the clock cluster, which is a real PLL driver rather than a mechanical substitution. `reflex_regops.h` also retires two ad-hoc copies of the same register accessor (`REG32` and `REG32_HAL`) and collapses seven ESP-IDF accessors to five — `SET_PERI_REG_MASK` routes through `ETS_UNCACHED_ADDR`, which on the C6 is the identity, so it and `REG_SET_BIT` were the same operation under two names.
- **`make soc-header` / `soc-check` / `soc-bridge` / `rom-check`** — the generator and the three gates that keep it honest, all wired into `make verify` and CI.

- **`make verify` and three new gates** — `warn-check` compiles the ESP-independent two thirds of the firmware at `-O2` with `-Wall -Wextra -Werror` (stricter than ESP-IDF's own flags); `lock-check` enforces that no `goose_telem_*` call happens while the loom lock is held; `idf-build` runs a real ESP-IDF build in the container image CI uses, so the firmware build can be verified without a local ESP-IDF install. `ci-lint` validates the workflow file's schema — renaming a CI job left `release`'s `needs:` pointing at a job that no longer existed, which GitHub rejects at parse time so that *no* jobs run and the only feedback is "a workflow file issue". `make verify` runs all of it plus the existing host, TASM and doc-link checks. Each gate was verified to *fail* on the defect it defends before being trusted — `idf-build` reproduces the exact CI error on the reintroduced truncation defect, `lock-check` flags both original telemetry sites, and `warn-check` found two real defects on its first run. Written because the previous remediation was pushed on the strength of `gcc -fsyntax-only` and broke all four ESP-IDF builds: a syntax check generates no code and runs none of GCC's flow-sensitive analyses. A stricter *host* compile was tried as the fix and measured to be insufficient — the truncation diagnostic comes from the RISC-V toolchain and is missed by host GCC 11 through 14 at every optimisation level — so `idf-build` is the one that actually closes the gap, and `warn-check` documents its own limits rather than implying otherwise.

- **RFC 4231 known-answer tests for the Aura MAC** — the crypto suite asserted that the HMAC was deterministic and that it changed when the key or message changed. All three hold for an implementation that computes the *wrong* digest, and because both sides of a mesh run the same code, a wrong-but-consistent SHA-256 would have authenticated every arc between two boards while being incompatible with every other HMAC-SHA-256 in existence. The implementation is in fact correct — verified byte-for-byte against OpenSSL across key lengths 1–140 — but nothing in the tree had established that. Cases 1, 2, 3, 6 and 7 are now asserted; case 6 carries a 131-byte key and is the first thing ever to execute the `key_len > 64` branch that folds the key through SHA-256. A 16-byte case pins the width the Aura key actually uses. 350 -> 355 host tests.

- **`docs/adoption-gaps.md`** — an assessment of what stands between the current substrate and something a hobbyist or lab can actually build on, written after the P0 remediation and registered in `implementation-status.md` as A1-A6. The finding is that the substrate is well ahead of the surface: a 12,738-entry register atlas, an authenticated mesh, role-based access and a ternary VM with an MMU are all real and working, and almost none of it is reachable without reading the C. - **Documentation gap sweep** — `docs/USER_MANUAL.md` was missing three registered commands (`kernel`, `loom`, `tapestry`) and had no coverage of the input rules or the `#R:` outcome marker; all are now documented, along with a warning that `vm run` blocks the shell. Extending the old grep pipeline would have reported false breakage across most of the tree, so it is now a script that both CI and a developer can run, verified to fail on a deliberately broken link. 102 relative links across 160 files currently resolve.
- **SDK rejects whitespace in single-token arguments** — the firmware now refuses extra tokens, so `node.purpose_set("my photography")` would have made a device round-trip and come back as "too many arguments". `_token()` raises a `ValueError` naming the field instead. The whitespace check runs *before* sanitizing, because tab is a control character and stripping first silently joined `a\tb` into `ab` — a quiet transformation of the caller's value, which is the failure the helper exists to prevent.
- **Extra arguments are refused instead of silently dropped** — `purpose set my purpose` stored the name `my`, discarded the rest and reported success: silent truncation *and* a false `+1,ok`, in the one feature built to make outcomes honest. There is no quoting, so a command handed more tokens than it consumes has lost operator intent rather than gained anything. Sixteen operand-taking commands now refuse with `#R:-1,invalid`. This was Key Decision 7 of `docs/lmm-shell-capabilities.md` Phase 1 and did not ship with the rest of it.
- **Four more handler paths reported success while failing** — `vm run` on an unknown program, `bonsai` GVM image load failure, the weaver collision check, and `atlas verify` when it finds duplicates or failures. All were reporting `#R:+1,ok`. The predictable cost of defaulting unmarked paths to engaged; found by sweeping failure-shaped prints for a missing `outcome()` call rather than by inspection.
- **Over-long input is refused instead of silently truncated** — past the line buffer the excess was dropped and the truncated line dispatched as though complete, which for `loom load` would have fed a *partial* fragment to a parser hardened against exactly that. Now reported as `#R:-1,overflow` with the line discarded. The ESP32 needed a second fix to make that guard reachable at all: its console reads via `getchar()` from a 128-byte hardware FIFO with no ring buffer, so a 1213-character line lost characters in transit and never reached the shell's bound. The UART console now installs a driver with an RX ring sized from `REFLEX_SHELL_LINE_MAX`, mirroring the USB-JTAG sizing on the C6. Both targets refuse at the same boundary, verified at 913/1022/1213/1513/2013 characters.
- **SDK `cmd_outcome()`** — returns `(text, Outcome)` from a single locked exchange. `last_outcome` is written inside `cmd()`'s lock and read after it is released, so it is racy when a node is shared across threads; `cmd_outcome()` is the safe form. `goonies find` on an unresolvable name now reports `#R:-1,notfound` rather than `ok`.
- **Ternary command outcomes (`#R:` marker)** — every command now emits a machine-readable result on its own line after its human output: `#R:+1,ok`, `#R:0,usage`, `#R:-1,denied|invalid|guard|notfound|failed`. The shell had always computed this and thrown it away — success, refusal and no-op are three distinct classes and `reflex_shell_dispatch` knows which at the moment it decides — leaving the SDK to reconstruct outcomes with `result.startswith("denied:")`, which made every human-readable string an undocumented API. The trit answers one question: did the intended state change occur? It is strictly more informative than an exit code, and the difference is load-bearing for an agent under `role="agent"`, which must distinguish *refused* from *ran and had nothing to report*. Additive — no existing message changed, so the Loom Viewer and any prose-matching consumer keep working. SDK: `node.last_outcome`, with `AccessDenied` now keyed on the marker. A reason implies its trit, so `#R:+1,denied` is unrepresentable; eight mutations verified against that invariant.
- **Line editing** — backspace and DEL were appended to the line buffer as literal bytes, so `statuX<DEL>s` dispatched as `statuX\x7fs` and any typo cost the whole line, including while typing a 32-character Aura key by hand.
- **Input line raised from 255 to 1023 characters** — the bound sat in front of an already-allocated 1024-byte buffer, capping `loom load` and `vm loadhex` — the only two ways to extend a running board — at 122 bytes of payload. This required growing the USB-JTAG driver's RX buffer too: at its 256-byte default the tail of a long line was silently dropped and the payload arrived as odd-length hex, so the transport is now sized from `REFLEX_SHELL_LINE_MAX`. Verified end-to-end at 200 and 500 bytes on both targets.
- **Repeatable hardware validation for the shell** — `tests/hardware/validate_shell.py`, wired up as `make hw-test PORT=/dev/cu.usbmodemXXXX`. 97 checks per board: the wire format, the full four-role dispatch matrix, the `tapestry` trit and `sys.*` guards against live cells, the hex rejection paths, and the SDK's `AccessDenied` contract. Non-destructive by construction — it never provisions or clears an Aura key (`aura clear` regenerates a *random* per-board key rather than restoring the old one, so it would silently un-pair a working bench), never reboots, and restores role, vitals and purpose. Validated on two C6s: 194/194.
- **Role-Based Access (RBA)** — capability-based session roles for the shell and Python SDK. Four roles: observer (read-only), agent (AI guardrail: purpose + snapshots), operator (day-to-day: LED, VM, mesh), admin (everything: reboot, aura, config). Every command classified by minimum role. `auth role <role>` restricts the session. SDK: `ReflexNode(port, role="agent")` with `AccessDenied` exception. Telemetry: `#T:U,<role>`. Default: admin (backward compatible). No PINs — voluntary capability declaration; PIN auth deferred to remote-shell phase.
- **Phase 33 Self-Expanding Perception (Curiosity Attractor)** — the OS is curious when purpose is active. A two-phase probe reads HARDWARE_IN shadow atlas registers 1 second apart; registers whose values changed are *hot* (alive) and get paged into the Loom. Hebbian learning decides which are relevant; eviction forgets the rest. Pain amplifies curiosity (doubled probe rate), not triggers it. Metabolic-gated (suspended in surviving, halved in conserving). Telemetry: `#T:D,<name>`. Shell: `status` shows curious/urgent/idle. No new files — a sub-pass of the existing supervisor.
- **SVD array register expansion** — the shadow atlas scraper now reads `<dim>` and `<dimIncrement>` from the SVD and generates entries for every array index. Shadow catalog grows from 9,527 to 12,738 entries: all 6 LEDC channels, all 3 DMA channels, all 35 GPIO pins, 128 GPIO input mux selectors, all RMT TX/RX channels, all PCNT units, and all crypto memory banks. Atlas bumped to v3.0.
- **Getting Started guide** — `docs/GETTING_STARTED.md`: 12-step guide from hardware purchase through build, flash, shell, Python SDK, and Loom Viewer. Covers macOS, Linux, and Windows with verification steps and troubleshooting at each stage.
- **Python SDK: vitals, telemetry, goonies read** — `vitals()`, `vitals_override()`, `vitals_clear()`, `telemetry_on()`, `telemetry_off()`, `goonies_read()` methods added to `ReflexNode`.

- **Ternary task disposition in the kernel policy layer** — the supervisor now decides a ternary stance per supervised field (`+1` engaged / `0` latent / `-1` withheld) and *derives* the host scheduler's integer priority from it, rather than computing a priority directly. `latent` means undecided and is deliberately distinct from `withheld`; a single priority number cannot express that difference. The aggregate is published as substrate state at `sys.kernel.disposition` and the per-field stance is readable via the new `kernel` shell command. This is ternary-native scheduling policy running on a binary scheduler the OS does not own — stated as such rather than overclaimed.

- **`loom evictions`** — reads the eviction ring, which had been written on every eviction since it was introduced and had no reader anywhere in the tree, costing an `snprintf` under `loom_authority` to fill a buffer nothing consumed. Reports the running eviction total and the most recent victims, which confirms directly that only shadow-paged and peer cells are ever chosen and seeds never are. Role: observer (read-only). `GOOSE_EVICTION_RING_SIZE` is now exported from `goose.h` so callers cannot under-size their buffer.

  The ring's own comment claimed it detected thrashing — the same cell repeatedly evicted and re-paged. It cannot, and never could: eviction is round-robin, so a re-paged cell lands behind the cursor and cannot be chosen again for a full lap of the table (~139 evictions at saturation), far outside a window of 8. That claim is corrected in the source and the command documents what it honestly shows. Real thrash detection would need a re-eviction rate over a long window and remains open.

### Fixed

- **Tier E's console work is one change, not two — established on hardware, not argued.** Owning receive means applying backpressure, because emptying the FIFO is what ACKs the USB packet and a receiver that always drains never slows the host down (measured without it: `console: 962 byte(s) DROPPED` on a 913-character line). But backpressure on receive deadlocks against a transmit path that blocks: `usj_write_bytes` spins until the host drains the IN endpoint, and a host driving the shell writes a whole line before it reads — so the device stops ACKing OUT, the host blocks mid-write and never reads, the device's IN endpoint fills, and the shell blocks in its echo and never calls the read that would re-arm the receiver. Both ends wait for the other. Observed as a console that serves short commands, passes 87 of 171 checks, then stops answering. The ESP-IDF driver does not avoid this by being cleverer about receive; it avoids it by buffering **both** directions. "stdio TX must move too" was recorded as a sequencing note and is stronger than that: RX alone is not a smaller first step, it is a step that cannot stand. The attempt, and a `reflex_hal_intr_set_enabled` that throttles at the interrupt controller rather than at the peripheral's shared `INT_ENA` register, are on branch `tier-e-console-rx`. `main` is unchanged and at 171/171 on hardware.

- **`make soc-bridge` could not run natively on macOS, so the proof it exists to provide had never been produced here.** The script has a native path for when `IDF_PATH` is set — no Docker — but it used `sed -i` with GNU syntax, which BSD sed reads as a backup suffix and rejects with "invalid command code" before compiling anything. Rewritten with a temp file. It now runs, and the previous commit's claim that 57 constants are `_Static_assert`ed against ESP-IDF is a demonstrated fact rather than an assertion: **"SoC bridge: 57 constants proved identical to ESP-IDF."**
- **Running it caught two real defects in those additions.** `REFLEX_INTR_SRC_USB_SERIAL_JTAG` was **39 and should be 48** — the enum-position script that produced it mishandled explicit `= N` assignments; the corrected method independently reproduces `ETS_SYSTIMER_TARGET1_INTR_SOURCE = 58`, matching the existing verified entry, which is what makes it trustworthy. A wrong interrupt source number routes a different peripheral's interrupt, which is exactly the defect the map records for the scheduler tick, and it would have shipped. Separately, the bridge did not include `soc/usb_serial_jtag_reg.h`, so two of the new field constants were not being checked at all — an assertion that cannot see its subject proves nothing, which is the same shape as every other check this session has had to repair.

- **A board dying *partway through* validation still aborted every board after it.** The previous fix handled failure at connect; a board that stops answering mid-run, or a parse that trips on an empty response, propagated out of `validate()` and took the rest of the invocation with it — the same defect at a different point. Anything unhandled is now recorded against that port as a named failure and the run continues. Deliberately broad and deliberately visible: the exception type and message are reported as a failed check, so a bug in the suite surfaces rather than being swallowed. Verified by injecting a mid-run exception into the first of two boards — one failure recorded, the second board fully validated at 170/171.

- **One unreachable board no longer aborts a multi-board validation run.** The readiness check added alongside this raised `SystemExit`, and `validate_shell.py` takes several ports on one command line — so the first board that did not answer would skip every board after it and print no summary at all. It now raises a dedicated `BoardNotReady`, caught per-port and recorded as a single failure while the run continues. `serial.SerialException` is caught with it, because a port that does not exist raises from `serial.Serial()` before readiness is ever consulted and aborts the run just as surely. Verified: a dead port followed by a live one gives `171 passed, 1 failed` and exit 1, a live board alone gives exit 0, and all three boards in one invocation give **512 passed, 0 failed, 1 skipped**.

- **`make hw-test` raced a booting board and reported 71 failures that were not there.** Running the suite immediately after `idf.py flash` on a classic ESP32 gave `99 passed, 71 failed`; re-running it unchanged gave `170 passed, 0 failed, 1 skipped`. Nothing was wrong with the firmware — every check was racing a board that had not reached its shell. `Board.__init__` settled for a fixed 0.6s, which is enough for a board that has been running and far too little for one just flashed. A suite that reports 71 failures for a timing reason is worse than one that waits: it sends someone hunting a defect that does not exist. It now polls `status` until the `#R:` marker comes back, so readiness means the shell parsed a command and answered rather than that some bytes arrived, and it fails with a diagnosable message if the board never responds.
- **Readiness now means stable, not merely alive.** One answer proved the shell was up but not that the console had finished settling: the first post-flash run still failed the 1022-character line check — the boundary case that most depends on the UART ring being fully up — while three later runs passed it. Two consecutive answers are required now. Verified across three flash-then-validate cycles on the classic ESP32 (170/171 each) and one on each C6 build (171/171 each), where previously the first run after a flash was unreliable.

- **The shell no longer reaches into peripheral registers it has no business knowing.** Adding the PLIC mask to the tick readback put a hardcoded `0x20001000` into `shell/shell.c` — the interrupt controller's base, already `#define`d in the C6 HAL — and three SYSTIMER offsets (`+0x64`, `+0x68`, `+0x70`) that `kernel/reflex_sched.c` already defines beside the code that programs them. The same register map written down twice, which goes stale silently. The controller mask is now a field on `reflex_intr_route_t` filled by the HAL, and the SYSTIMER state comes from a new `reflex_sched_tick_debug` accessor next to the offsets it reads. Zero raw register pokes remain in the shell; the readback is byte-identical on hardware, and both builds still pass `make hw-test` 171/171.

- **`reflex_sched_start` armed the scheduler tick without routing it.** It called `setup_systimer_tick()` directly — enabling the comparator and the peripheral interrupt and stopping there, with nothing mapping the source through the interrupt matrix, setting a PLIC priority, or enabling the `mie` bit. That is the exact hazard that stops the core: `SYSTIMER_TARGET1`'s matrix entry holds its reset value of 0, so the comparator asserts onto CPU line 0, level-triggered and permanent. Starting the scheduler would have hit it on the very first tick. It now calls `reflex_sched_tick_start`, so the scheduler's tick and `kernel tick`'s tick are the same code path — the one measured at 6/6 cold starts, 1000-1001 Hz, on both builds.
- **The `mtvec` hand-off is quantified rather than described.** `kernel tick` now reports the whole PLIC enable mask, captured live: `0x0b001f24` — ten lines, of which **nine belong to ESP-IDF** (2, 5, 8, 9, 11, 12, 24, 25, 27 on the 802.15.4 build) and one is Reflex's tick. Owning the trap vector means servicing or re-homing all nine — the console, the radio, the timer and what sits behind them — which is the concrete size of the job the map has always described as "owning startup outright". The mask is sampled live rather than after teardown, which would have excluded Reflex's own line and quietly reported a smaller number than the one that matters.

- **The Reflex-owned scheduler tick fires at 1000 Hz on the independence configuration.** ESP32-C6 with `CONFIG_REFLEX_RADIO_802154` and `CONFIG_REFLEX_KERNEL_SCHEDULER`, through Reflex's own interrupt-matrix, PLIC, `mie` and ROM-vector programming with no `esp_intr_alloc` in the path: **6/6 verified cold starts at 1000-1001 Hz**. That is C2's remaining debt paid on the path that actually matters, and it is what C3 was waiting behind.
- **"TICK-B" was never a separate defect, and saying it was is worth recording.** The 802.15.4 build appeared to have its own total-non-delivery bug because the test that should have shown the threshold-derived priority working ran against a build that *also* carried PLIC-aware line allocation — which moves off CPU line 10 and breaks delivery outright. One change masked the other and the conclusion drawn, that the priority fix did nothing, was wrong. Two variables, one experiment. The accumulated fixes — the comparator work-enable bit, routing before arming, installing the vector before the line is deliverable, and priority above the live threshold — close it together.
- **TICK-A remains on both builds** and is now correctly scoped: the first arming after a cold boot runs at 1000 Hz, every later arming delivers one tick. The scheduler arms once at start and never re-arms, so this is correctness debt rather than a gate on Tier C. Bisection has exonerated interrupt-line management and left `setup_systimer_tick` and the SYSTIMER teardown.

- **The host suite did not rebuild when a header changed, so header-only changes were silently untested.** `tests/host/Makefile` listed only `$(SRCS)` as prerequisites for the binary, so editing a header left the previous build in place and the suite re-ran it. Found by mutating `reflex_intr_priority_for` — a `static inline` in `include/reflex_hal.h` — and watching the test that pins it report a pass; it fails correctly after a `make clean`, and now fails without one. The same class of defect as a format gate that cannot fail: a check that does not run is indistinguishable from one that passes. Headers are prerequisites now, verified by observing zero compile steps before touching one and one after.
- **The PLIC priority rule is extracted and host-tested.** It was added during debugging and kept "on its own merits", which is exactly the kind of change that should not sit untested in a hardware abstraction layer. It is pure arithmetic — the controller forwards only *above* the threshold — so it is now `reflex_intr_priority_for` in `reflex_hal.h`, pinned by 8 assertions including the saturation case, where the old inline arithmetic would have wrapped `UINT32_MAX + 1` to 0 and produced a priority the controller reads as "never delivered". Verified to fail when the guard is removed.
- **The two scheduler-tick failures are named separately and will not be conflated again.** TICK-A is the re-arm failure on the default build, where a cold arming works at 1000 Hz. TICK-B is total non-delivery on the 802.15.4 build, where not even a cold arming has ever fired. They are different problems, the independence path needs TICK-B, and a fix for one proves nothing about the other — the threshold-derived priority was first tested only against TICK-B, on a configuration that could not have shown a result either way.

- **Bisected the re-arm failure to the comparator, exonerating interrupt-line management.** `tick_stop` released the CPU interrupt line on every stop and `tick_start` re-claimed it, making the allocate/free cycle the obvious suspect — and the routing readback showing every controller register identical between a working and failing arming pointed the same way. Claiming the line once and keeping it across arm/disarm changes nothing: arming 1 still runs at 1000 Hz and armings 2 through 6 still deliver exactly one tick each. The change was reverted because its entire justification was the hypothesis it disproved. What remains is `setup_systimer_tick` and the SYSTIMER teardown, and the symptom is sharper for it — **exactly one** tick per re-arming means the comparator fires and does not reload, though period mode should re-arm it, which points at `SYSTIMER_TARGET1_CONF` or the `COMP1_LOAD` latch not taking on a second arming.

- **The `mip` reading was tautological, and the routing readback could not see the working case.** Both are fixed and both were my own defects. `mip` was read with `mstatus.MIE` set — the state a shell command runs in — where a forwarded interrupt is taken before the read can observe it, so `mip=0` was guaranteed whether the controller was forwarding or not; it is now read with traps masked, which makes `0` genuinely mean "not forwarded". And the readback printed only when the tick failed, so the working case had never been observed and a claim about it went into the record unmeasured. It now prints on success too.
- **That claim was false: a cold arming does not run at `thresh=0`.** Comparing a working arming against a failing one on the same boot, every controller register is identical — `intmtx src=58 -> cpu_int=10`, `plic enabled=1 pri=2 thresh=1 level=1`, `csr mie=1 mip_pending=0 mstatus.MIE=1`. The threshold is 1 in both, so deriving priority from it is correctness rather than the explanation of anything, and the code now says so where it previously claimed otherwise. **The single observable difference is the SYSTIMER source: `raw=0x0 st=0x0` when it works, `raw=0x2 st=0x2` when it does not** — stuck asserted from a firing that no ISR ever acknowledged.

- **The re-arm failure is narrowed to interrupt forwarding, by adding `mip` to the routing readback.** On a failing re-arm the core reports `mip_pending=0` while the SYSTIMER source is asserting *and* latched (`raw=0x2 st=0x2`), routed to CPU line 10, PLIC-enabled, with `mie` and `mstatus.MIE` set. The core never sees the interrupt, so nothing downstream is masking it and the trap path is irrelevant — the controller is not forwarding an asserted, routed, enabled line. That rules out most of what had been suspected and leaves two candidates, neither currently observable: an in-service state latched by the first tick and never released, and controller state `reflex_hal_intr_free` does not restore.
- **Priority now derives from the live PLIC threshold**, kept on its own merits rather than as a fix. The controller forwards only *above* `MXINT_THRESH`, so `pri=1` against `thresh=1` violates the rule — a cold arming happens to run at `thresh=0`, which is why it worked by luck. Tested twice as a fix for the re-arm failure and rejected both times, most recently with `pri=2` over `thresh=1` still delivering nothing. Cold starts remain 5/5 at 1000-1001 Hz with it in place.

- **The Reflex-routed scheduler tick is delivered on hardware for the first time.** Three defects stood between "routed" and "firing", none visible to a compiler, a linker or any gate here. `setup_systimer_tick` wrote `SYSTIMER_CONF |= 1 << 25` where `TARGET1_WORK_EN` is **bit 23** — ESP-IDF's own `systimer_ll_enable_alarm` computes it as `1 << (24 - alarm_id)`, and bit 25 is `TIMER_UNIT1_CORE1_STALL_EN`, which does nothing observable on a single-core part; the comparator was simply never enabled, read off a board as `raw=0x00000000` with the interrupt routed all the way to the CPU. `reflex_sched_tick_start` then armed the comparator *before* routing it, so TARGET1 asserted while its interrupt-matrix entry still held its reset value of 0 — onto CPU line 0, level-triggered, and the core stopped making progress with the idle task starved into a watchdog timeout; routing now happens first, because a routed line with an unarmed source is inert while an armed source with no routing is not. And `reflex_hal_intr_alloc` enabled the PLIC line and re-enabled interrupts *before* installing the ROM vector, leaving a window in which an already-asserting source is taken with no handler — for a level interrupt that is permanent, not a missed event. The PLIC enable is now the last step.
- **`kernel tick` reports the routing, not a conclusion.** "Routed but not firing" names four possible causes and distinguishes none of them; a readback distinguishes all of them and is three reads away. It now prints the interrupt-matrix entry, PLIC enable/priority/threshold/type, the `mie` and `mstatus.MIE` bits, and the SYSTIMER enable/raw/status registers — every value read back from hardware at that moment rather than remembered from setup, because the interesting failure is the one where something else changed it. Backed by a new `reflex_hal_intr_describe` in the HAL. The first version of this readback ran *after* `reflex_sched_tick_stop()` and so described the teardown rather than the failure; the fix and the reason are recorded in place, since that is precisely the mistake the readback exists to stop someone making from the outside.
- **Correcting the entry above: the tick fires intermittently, and the earlier claims about it were drawn from single samples.** Best measurements on the default build are `497 ticks in 496930 us -> 1000 Hz` and `500 ticks in 499157 us -> 1001 Hz`, so when it fires it fires at the target and the 16 MHz period derivation is right. But the same image measured 0 Hz on other boots. A reading that the first arming after boot works and re-arming does not fitted four consecutive runs and then failed to reproduce; it is recorded as a discarded hypothesis, not a finding. Three further changes were tried and all three reverted after measurement: PLIC-aware line allocation (looks obviously correct, *broke the working case* — the tick runs on CPU line 10 and moving off it delivers nothing, so the original "line 10 is verified safe" note is load-bearing empirical knowledge), priority derived from the live PLIC threshold (`pri=2` over `thresh=1` changed nothing), and reordering the arming sequence (enabling the comparator before latching `COMP1_LOAD` dropped a working arming to one tick; ESP-IDF's configure-latch-enable order is correct). The three ordering and bit fixes that took the tick from *never* firing to *sometimes* firing at the right rate remain. Delivery on the 802.15.4 build has never been observed at all, with the source asserting and latched and everything downstream verified correct.

- **The 802.15.4 radio backend recursed until the stack was gone, and it was blocking the entire independence path.** `CONFIG_REFLEX_KERNEL_SCHEDULER=y` with `CONFIG_REFLEX_RADIO_802154=y` — the configuration ESP-IDF independence is pursued on — panicked at boot and then halted under Boot0's loop protection. Reproduced on hardware: the stack dump is a seven-frame pattern repeating to exhaustion, and decoding it names the cycle exactly — `esp_ieee802154_transmit_failed` (ours) → `esp_ieee802154_receive` → `ieee802154_receive` → `rx_init` → `stop_current_operation` → `ieee802154_ll_clear_events` → `ieee802154_inner_transmit_failed` → back to ours. Both TX callbacks called `esp_ieee802154_receive()` to return the radio to RX, and the driver signals transmit-failed from inside its own event dispatch, so re-entering it from that callback made it signal again. The driver already does this itself: `next_operation()` calls `enable_rx()` when the `rx_when_idle` PIB flag is set, and it defaults to false — which is what the manual re-arm was compensating for. `esp_ieee802154_set_rx_when_idle(true)` at init removes the re-entrancy instead of guarding it, and both callbacks now do nothing. A whitelist, not a blacklist: a coupling mode added to the enum later must be considered deliberately rather than becoming wire-reachable the moment it is defined, and `_Static_assert`s bind the mirrored constants to `goose_coupling_t`. This matches what `tools/loomc.py` already emits, so no existing fragment changes meaning.
- **`trans_count` was parsed and silently ignored** — a fragment could declare transitions, watch the weave report success, and never learn the behaviour it asked for was dropped, since no transition format is implemented. Now refused with `REFLEX_ERR_NOT_SUPPORTED`.
- **`goose_supervisor_rebalance` mutated routes with no loom lock** — it wrote `r->orientation` outside `loom_authority` and then called `goose_process_transitions`, which takes the lock at depth 0, violating the supervisor's own discipline that every route mutation is lock-guarded. Benign on the single-core C6, where the supervisor cannot preempt itself mid-write; genuinely racy on the dual-core ESP32, where the supervisor task (priority 20) and unpinned field pulse tasks (priority 10) run in parallel, so the write races the pulse's route reads. Now takes `goose_loom_try_lock` with the established timeout-and-skip semantics, and releases it *before* `goose_process_transitions` — the lock is a non-recursive test-and-set, so holding it across a function that re-acquires it would spin to timeout and skip the very propagation the repair exists to perform.

- **Mesh replay cache ignored the sender MAC entirely** — `replay_slot_index` XOR'd the last two MAC bytes in at bit positions 8-23 and then masked the low 6 bits, so the slot was exactly `nonce & 63` for *every* peer. Nonces come from a monotonic microsecond clock, so a second peer whose uptime led by a multiple of 64 µs — or any key-holder choosing a nonce — evicted a victim's entry and reopened the 5-second window the guard exists to close. `SECURITY.md` §4 described the blend as working; it never did. The hash now covers the full MAC and mixes every input bit down into the index, and lives in `goose_policy.c` so the host suite exercises the firmware's own function rather than a restatement of it — 64 peers sharing a nonce previously landed in 1 slot, now in more than half the ring.

Defence-in-depth rather than a live escape — but rejecting a bad image up front instead of relying on the layer below is the loader's entire purpose. ### Security

- **Unvalidated arc state let one packet hijack swarm consensus** — every consumer of `arc->state` treats it as a trit: SYNC and MMIO_SYNC assign it directly into a cell's `state`, and POSTURE multiplies it by the wire weight into the swarm accumulator. Nothing validated it on either end. The protections SECURITY.md §7 claims — Inertial Hysteresis and Accumulator Saturation — are arithmetic that only holds while `|state| <= 1`; with weight capped at 4 a legitimate arc moves the accumulator by at most 4 against a threshold of 10, so consensus needs several cooperating arcs. An arc carrying `state=99` moved it by 396 and saturated immediately. Demonstrated on hardware with a guard-removed build: **a single** malformed arc flipped a peer's posture. `atmosphere_recv_cb` now range-checks state once at ingress — after the Aura gate, before op dispatch, so no future op can miss it — and drops the arc, counting it in the new `rx_malformed`, surfaced by `mesh stat`. Verified on hardware: five malformed arcs counted and discarded with the posture cell unmoved and `rx_posture` unchanged, while well-formed arcs still drive consensus normally.
- **`mesh posture` was the same defect as `tapestry signal`, and it transmits** — `int8_t state = (int8_t)atoi(argv[2])` with no range check at all, so a typo went onto the radio Aura-authenticated. Now parsed with `shell_parse_trit`, and the weight with `shell_parse_int`. The remaining `atoi`/`strtoul` sites went with it: `mesh emit` (range-checked but still coercing `abc` to 0), `config set log_level` and `boot_count`, and `mesh peer add`, whose MAC *format* was checked while its hex pairs were not — `zz:zz:zz:zz:zz:zz` registered a peer at `00:00:00:00:00:00`. `sleep` was already safe by virtue of its `< 1` clamp.
- **`aura setkey` accepted non-hex and silently provisioned a zero key** — all three operator-facing hex parsers (`aura setkey`, `loom load`, `vm loadhex`) decoded with `strtoul(pair, NULL, 16)`, which returns 0 for any non-hex input without signalling — the same silent-coercion class as `atoi("abc")` being a valid trit. For `loom load` and `vm loadhex` it was benign: the CRC and `goose_weave_loom`'s structural validation reject the garbage downstream. `aura setkey` has no downstream check, because those 16 bytes *are* the mesh HMAC key that SECURITY.md §4 relies on to prevent geometric spoofing. `aura setkey <32 non-hex chars>` provisioned an all-zero key — a guessable shared secret — and printed "aura: key provisioned", indistinguishable from success. All three now share `shell_parse_hex`, which validates the entire string before writing a byte, so a partially-typo'd key can never reach NVS. Nine mutations verified to fail the suite, including one that restores the original defect exactly.
- **Shell input parsing split from access-control policy** — `shell_parse_trit` had been living in `shell_policy.c`, which is about *who may run a command*, not *how operator text becomes a typed value*. Parsing now has its own translation unit (`shell/shell_parse.{c,h}`) and its own suite (`tests/host/test_shell_parse.c`). Host suite: 258 → 284 assertions.
- **The SDK's `AccessDenied` never fired — the shell echoed no newline on Enter** — SECURITY.md §2 promised that a command exceeding the session role raises `AccessDenied` in the Python SDK. It never did. `reflex_shell_run` dispatched on `'\n'` without echoing one, so a command's echo and its response shared a line on the wire (`b'led ondenied: requires operator\r\n'`). The SDK strips the echo line-wise, so nothing was stripped, `result.startswith("denied:")` was never true, and the exception was never raised — a role-restricted caller got a string back and carried on as though the command had succeeded. That is precisely the case the role model exists to serve: an AI agent constrained via `ReflexNode(port, role="agent")`. The shell now echoes the newline before dispatch, which makes the wire line-oriented and fixes every consumer at once rather than patching one parser. Hardware-verified on two C6s: `AccessDenied` raises, and string-returning SDK methods no longer carry an echo prefix.
- **Role-Based Access is now testable, tested, and fails closed** — the enforcement point for the whole role model lived in `shell.c`, which the host suite does not compile, so nothing pinned it. The role table and sub-command escalation rules moved to `shell/shell_policy.c` behind `shell_required_role()`; `shell.c` keeps only the handlers and the session role, so the two cannot drift. A command with no policy entry now requires `admin` instead of falling through to `observer`. `tests/host/test_shell_policy.c` covers every command and sub-command against the SECURITY.md §2 table; nine mutations were each verified to fail it. Host suite: 170 → 258 assertions.
- **`tapestry signal` hardened, and documented for the first time** — the command wrote `atoi(argv[3])` straight into a cell's `state` field with no validation of any kind. Three defects in four lines: the value was cast to `reflex_trit_t` (a three-value enum) without a range check, so `tapestry signal <cell> 99` stored 99 and broke the trit invariant every consumer relies on; `goose_fabric_get_cell` resolves any name, so an `operator` could write `sys.kernel.disposition` or any other supervisor cell, contradicting the `sys.*` namespace rule the MMIO sync layer already enforces on remote writes (SECURITY.md §8); and a malformed invocation returned silently, the same bug class the comment above `shell_cmd_bonsai` documents having already been fixed once. The state is now range-checked, `sys.*` is refused before resolution, and a bad invocation prints usage. The command was absent from the README table, the user manual and `help` — it was the only registered command with no user-facing documentation anywhere. Now in all three.
- **Strict trit parsing for operator-supplied states** — `atoi("abc")` returns 0, itself a valid trit, so a typo silently signalled zero instead of erroring. `tapestry signal` and `vitals override` now share `shell_parse_trit`, which rejects trailing garbage and out-of-range values.
- **`config` reported nothing on a malformed invocation** — same silent-no-op shape as `tapestry`; it now prints usage. `README.md` also gained the `kernel` and `aura clear` rows, which were implemented and in `help` but missing from the command table, and the `vitals override` row now names the `pain`/`reward` signals the code accepts.
- **Boot image verification** — `reflex_boot0` now verifies the SHA-256 that `esptool` appends to the image, using the ROM SHA engine, *before* any segment is copied into RAM; a mismatch refuses the boot. Segment destinations are bounds-checked against the true RAM windows, so a malformed image can no longer write past SRAM or the LP window over boot0's own stack. The digest is unsigned — this is corruption detection, not authentication. See [`SECURITY.md`](SECURITY.md) §0.
- **Sanctuary Guard now covers probing** — `goose_supervisor_explore` read raw MMIO from the shadow atlas before any guard ran; `is_sanctuary_address` was only consulted when *binding* a cell. Reads are not side-effect-free (read-to-clear status registers, peripheral FIFOs), so the guard is now applied at both the probe gate and the confirming re-read.
- **LoomScript loader hardened** — `goose_weave_loom` treated wire data as trusted: `uint16_t` route indices were never bounds-checked against `cell_count`, unresolved cells were dereferenced, declared array sizes were trusted past the end of the buffer, and route memory was left uninitialised. All validated up front now, ahead of `prd-tasm-upload.md` making this path reachable.

- **Shadow atlas int8_t overflow** — widened `shadow_node_t::c` to `int16_t` and added `goose_make_shadow_coord` that encodes wide cell indices across `trits[6]` and `trits[7]` without truncation. Closed ~100 `-Woverflow` warnings.
- **Alloc/pulse lock cycle** — `goose_fabric_alloc_cell` now takes `loom_authority` before `fabric_mux`, serializing against the pulse reader. Lock order: `loom → fabric`.
- **autonomy_field route append race** — `goose_supervisor_weave_sync` now holds `loom_authority` around the append block and publishes `route_count` via `__atomic_store_n(..., __ATOMIC_RELEASE)`.
- **Hebbian learn_sync mutation race** — the plasticity pass now holds `loom_authority` across all per-route mutations.
- **Short-circuit alloc goonies_register** — the coord-already-exists path now keeps `loom_authority` held across the `goonies_register` call for consistency with the main path.
- **Replay cache window** — `last_us` is now actually read; stale entries are treated as empty, and the slot index blends the last two MAC bytes into the hash to reduce cross-peer false positives.
- **Aura fail-closed** — HMAC computation errors return a non-matchable sentinel (`0xDEADBEEF`) plus `ESP_LOGE`, preventing a transient mbedtls failure from producing `aura=0` on both sides.
- **Posture weight cap** — `ARC_OP_POSTURE` handling clamps the per-packet weight at `SWARM_WEIGHT_MAX=4` on both emit and receive, so a single rogue peer cannot cross `SWARM_THRESHOLD=10` alone.
- **Unchecked malloc in `goose_supervisor_weave_sync`** — autonomy_field allocation now frees partial state and returns `ESP_ERR_NO_MEM` on failure.
- **Signed/unsigned compare** in `goose_fabric_get_cell_by_coord` cleaned up with an explicit `(uint32_t)idx` cast.
- **LP core variant** — ESP32-C6 uses the `LP_CORE` ULP variant, not `RISCV`. Earlier attempts at enabling the wrong variant are now corrected in `sdkconfig.defaults`.
