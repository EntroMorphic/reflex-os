# Codebase Audit — 2026-09-04

Successor to [`audit-2026-08-12.md`](audit-2026-08-12.md). Assessment of the Reflex OS
codebase at commit `676f7fb`, after the Phase 1 shell-capabilities work and the
documentation sweep that followed it.

Every finding below was remediated in the same pass; each entry states what was
wrong, how it was confirmed, and what changed.

---

## 1. Scope and Method

First-hand reading, consistent with both prior audits. No subagents.

`goose_shadow_atlas.c` is 12,778 of the tree's 31,545 C/H/S lines and is machine-generated
from the SVD. The hand-written firmware surface is **16,044 lines**; tests add 2,723.

| Depth | Files |

| **Read in part** | `goose_runtime.c` (allocator, lock discipline, telemetry deferral), `shell.c` (every handler's failure paths), `goose_supervisor.c` (lock/telemetry cross-reference), `sdk/python/reflex.py` |

**What was executed, not just read:**

- Host suite: **350 passed, 0 failed** at audit start (355 after this pass adds crypto vectors).
- `tests/host/test_tasm.py` and `tools/check_doc_links.py`: both clean (102 links, 160 files).

## 2. State of the Codebase

Better than the two prior audits found, and worth recording as such:

- **Zero** `TODO`, `FIXME`, `XXX` or `HACK` markers in the tree.
- **Zero** uses of `strcpy`, `strcat`, `sprintf`, `gets` or `alloca` in firmware.
- `shell_policy.c` fails closed: a command in the dispatch table but absent from the policy table

The findings are correspondingly narrow. Most are a single class: **a layer added late was not
retrofitted to the code that predates it.**

## 3. Findings

### 3.1 Telemetry performed blocking console I/O inside the loom lock — HIGH

`goose_runtime.c`, in `fabric_alloc_internal`: `goose_telem_evict` and `goose_telem_alloc` were
called while holding **both** `loom_authority` and `fabric_mux`. `reflex_critical_enter` is
`taskENTER_CRITICAL`, so this ran with interrupts disabled.

`goose_telem_*` writes to the console through `reflex_hal_write_raw`. On the C6 that is
`usj_write_bytes`, which spins on a USB-JTAG FIFO **per byte**, up to `USJ_TX_SPIN_LIMIT`
(20,000) iterations each, and returns early only when no reader is attached. On the ESP32 it is
`fwrite` + `fflush`.

The budget these two calls sat inside is `LOOM_LOCK_TIMEOUT_US = 300`, against the steady-state
peak hold of 353 µs recorded in `implementation-status.md`. A single console write is orders of
magnitude past that. The trigger condition is precisely when the Loom Viewer is in use and the
fabric is saturated — where every allocation also evicts, so two writes happen per allocation
under the lock. That is the `LOOM_CONTENTION_FAULT` class that commit `a249b2e` fixed for flash
I/O, reintroduced through a different door.

This was an outlier, not a design choice. Every other telemetry site in the substrate already
snapshots inside the lock and emits after unlocking — `internal_process_transitions` maintains a
`telem_defer_t` buffer for exactly this, and `goose_supervisor.c:651` carries the comment
*"serialised; the flash write must not hold it."* `reflex_hal_esp32c6.c` names the hazard directly:
a lock *"would have to be held across `usj_write_bytes` and therefore across a spin on a USB FIFO."*

**Fixed.** Both emissions now snapshot into locals inside the lock and emit after both locks drop,
matching the existing idiom. The snapshot is gated on `goose_telemetry_enabled`, so the default
(telemetry off) path costs nothing. The eviction name is copied — the registry entry is removed
moments later — into a 40-byte buffer, matching the documented telemetry name width rather than
widening the locked region's stack footprint.

> Note on the scheduler: the defect is not FreeRTOS-specific and the fix is not either. Blocking
> console I/O inside an interrupt-disabled critical section is wrong under any scheduler, including
> `reflex_task_kernel`. Nothing in the remediation adds a dependency.

### 3.2 The ternary outcome contract was incomplete — MEDIUM

`s_outcome` defaults to `SHELL_OK`, so any path that returns without calling `outcome()` reports
`#R:+1,ok`. Since `580a497` that marker is the SDK's contract — `AccessDenied` is keyed on it and
`ReflexNode.last_outcome` is the documented way an agent distinguishes *refused* from *ran and had
nothing to report*. Sixteen paths were answering that question wrongly.

**The Sanctuary Guard was the worst of them.** All three refusals in `goonies read` returned with
no outcome, so a guard that exists to stop an MMIO read from clearing status bits or popping a live
FIFO reported success while refusing. `shell_outcome.h` documents `SHELL_GUARD` as *"refused by a
policy guard (sanctuary, `sys.*`)"* — the enum value was written for this case and never emitted
for it. The gap was untested: `validate_shell.py` asserted `guard` only for `tapestry signal sys.*`.

The rest:

| Path | Was | Now |
|---|---|---|
| `goonies read` sanctuary refusal (×3) | `+1,ok` | `-1,guard` |
| `snapshot save` / `load` / `clear` | `+1,ok` regardless of `rc` | `-1,failed` on error |
| `mesh emit` / `query` / `posture` / `ping` / `peer add` | `+1,ok` regardless of `rc` | `-1,failed` on error |
| `config set boot_count <non-integer>` | `+1,ok` | `-1,invalid` |
| `mesh peer add` with wrong MAC separators | `+1,ok` | `-1,invalid` |
| `snapshot` / `purpose` bare usage | `+1,ok` | `0,usage` |
| `kernel` with no fields, `vm list` empty, `loom evictions` none | `+1,ok` | `0,none` |

The `rc`-printing handlers all predate the outcome marker: they print `rc=0x%x`, which tells a
human what happened and the SDK nothing. A single `outcome_rc()` helper now maps the code rather
than repeating the branch nine times. Contract cases for the guard, the parser rejections and the
usage paths were added to `validate_shell.py`.

### 3.3 `mesh peer add` silently truncated the peer name — MEDIUM

`reflex_peer_t::name` is 12 bytes; `strncpy` kept 11 characters and returned `REFLEX_OK`. The shell
then echoed back **`argv`**, not what was stored — so the confirmation line named a peer that
`mesh peer ls` would never show.

**Fixed** on the rule the goonies registry already follows for atlas names: an over-long name is
**refused**, not truncated. Both mesh-side callers are well inside the bound (DISCOVER carries at
most 8 bytes; auto-registration formats `auto_xxxx`), so nothing on the wire is affected. The shell
now names the limit on rejection and echoes the *stored* name on success.

### 3.4 `mesh status` totals omitted DISCOVER — LOW-MEDIUM

`rx_total` excluded `rx_discover`; `tx_total` was `tx_mmio_sync` alone, excluding the `tx_discover`
the struct already tracked and `mesh stat` already printed. A board broadcasting discovery beacons
since boot reported `tx=0`. This is the same omission `mesh stat` was fixed for — its handler
carries the comment explaining that leaving DISCOVER out *"reads as a dead mesh"* — applied there
and not here.

Worse, four ops had no TX counter at all, so README's "total RX/TX" claimed more than was measured.
**Fixed:** `tx_sync`, `tx_query`, `tx_advertise` and `tx_posture` added and incremented at each emit
site; both totals now cover every op; `mesh stat` prints the new counters.

### 3.5 `mesh_stats` was read under a lock its writers never took — LOW

`goose_atmosphere_get_stats` acquired `swarm_mux` to copy the struct. Not one of the thirteen
`mesh_stats.*++` sites held it — they run in the radio receive callback. The lock protected nothing
while reading as though the snapshot were serialised, which is worse than no lock at all. The
increments are read-modify-write, so a preemption between load and store drops one outright, and on
the dual-core ESP32 the two can genuinely race.

**Fixed** with `__atomic_fetch_add(..., __ATOMIC_RELAXED)` per counter and the misleading lock
removed from the getter. Relaxed is the correct model: these counters carry no happens-before
relationship to anything, they are only observed for their own value. Each field is a
naturally-aligned `uint32_t` so no counter reads torn; the snapshot as a whole is not one instant,
which is the right trade for observability and is documented as such.

### 3.6 A peer rename never reached NVS — LOW

`goose_mmio_sync_add_peer` called `peers_save_nvs()` only when appending. Re-adding a known MAC
under a new name updated RAM and returned OK, so the rename held until the next reboot and then
silently reverted. **Fixed:** the update path persists when the name actually changed.

### 3.7 Stale comment on the Aura fail-closed path — LOW

`calculate_aura` documented its sentinel as guarding against *"any mbedtls error."* mbedtls was
removed in the crypto consolidation (`979fbbb`); the MAC comes from `reflex_crypto.c`, which cannot
currently fail — so the branch is defence in depth, not a live path. The comment also still
described the retired 32-bit MAC width. **Corrected.** The branch is kept deliberately: an aura that
silently degrades to a predictable value is exactly the failure it must never have.

### 3.8 README's line count did not reconcile — DOC

README claimed "~26,000 lines of C and assembly." Measured: **16,044** hand-written (C/H/S,
excluding tests and the generated atlas), **28,822** including the atlas, **31,545** including
tests. No natural counting produced ~26,000. **Corrected** to state both figures and which is which.

### 3.9 The crypto suite tested determinism, not correctness — MEDIUM (test gap)

`test_crypto` asserted that the MAC was deterministic and that it changed when the key or message
changed. All three hold for an implementation that computes the *wrong* digest. Because both sides
of a mesh run this same code, a wrong-but-consistent SHA-256 would have authenticated every arc
between two boards happily while being incompatible with every other HMAC-SHA-256 in existence —
and no test in the tree would have noticed.

The implementation is in fact **correct**: verified byte-for-byte against OpenSSL across key lengths
1–140 and RFC 4231 cases 1, 2, 3, 6 and 7. The gap was in the testing, not the code.

**Fixed:** the RFC 4231 known-answer vectors are now asserted, including case 6 — a 131-byte key,
which exercises the `key_len > 64` branch that folds the key through SHA-256 first and which nothing
had ever executed. A 16-byte case matching the Aura key width is included, cross-checked against
OpenSSL since the RFC has none. Host suite: 350 → 355.

### 3.10 Implicit declaration of `malloc` — LOW

`goose_runtime.c` calls `malloc` without including `<stdlib.h>`, reaching it transitively under
ESP-IDF. Implicit declaration is an error from C11 onward and would truncate the pointer on any
64-bit host build. **Fixed** with the include.

### 3.11 A second missing `<stdlib.h>` — LOW

`goose_library.c` calls `malloc` and `free` with no `<stdlib.h>`, the same
defect as 3.10 and missed by the same reading pass that caught the first. Found
by the warning gate built in §5, on its first run. **Fixed.**

### 3.12 `reflex_radio_send`'s header promises addressing one backend does not honour — MEDIUM (doc)

`goose_atmosphere_advertise` accepts the querier's `dest_mac` and broadcasts
anyway, which looks like a plain oversight. It is not: `reflex_radio_send`
treats `dest_mac` as advisory, and the IEEE 802.15.4 backend — the blob-free
mode the README leads with — discards it entirely and always emits a broadcast
frame (`build_broadcast_frame`). The header nevertheless documented the
parameter as "Six-byte destination, or the all-`0xFF` broadcast address", which
is simply false for one of the two shipped radios.

Nothing is broken today: all six call sites already pass the broadcast address,
so no code relies on a promise that would not be kept. The risk is entirely
future — someone writing a directed reply against that contract would get a
silent broadcast under 802.15.4 and might build a confidentiality assumption on
it. **Fixed** in the header, which now states the divergence and points out
that the Aura MAC, not the destination address, is what restricts who can act
on an arc. `goose_atmosphere_advertise` keeps the parameter with an explicit
`(void)` and the reasoning recorded, rather than being changed to unicast and
behaving differently on the two radios.

### 3.13 `make format-check` could not fail — MEDIUM

The recipe piped `clang-format` into `head -20`, so the exit status was
`head`'s — always zero — and the next line printed "Format check passed."
unconditionally. It reported success while listing violations. The CI job has
therefore been green for its entire existence, including on commits that
violated the style it claimed to enforce, and `.githooks/pre-commit` (which is
written correctly) was never installed via `core.hooksPath`, so nothing checked
formatting at any point.

Tree-wide the repository does not satisfy its own `.clang-format`, and
reformatting it wholesale would bury history in `git blame` — a decision worth
making deliberately, not as a side effect of fixing a broken check.
**Fixed** in two parts: `format-check` now reports truthfully and exits
non-zero, and CI gates a new `format-diff` target that checks only the lines a
change touches, so the tree converges without a mass reformat.

### 3.14 Telemetry line atomicity on the allocation path — LOW (property change, not a defect)

Recorded because the fix in 3.1 changed a property nobody chose. Holding the
loom across the console write incidentally serialised the allocation path's
telemetry; emitting after unlock means two concurrent allocations can now
interleave their output byte-wise. This matches every other telemetry site in
the substrate and `reflex_hal_log` already accepts it explicitly — the
alternative is holding a lock across a spin on a USB FIFO, which is the defect
being fixed. Conformance, not regression, but a consumer that assumed atomic
lines from that path should know the assumption was always weaker than it
looked and is now weaker still.

### 3.15 `mesh peer add` is a breaking change — LOW

Peer names longer than 11 characters were truncated and are now refused
(3.3). Input that previously appeared to succeed will now return
`#R:-1,invalid`. Intended, and the right direction, but it is a behaviour
change for any script that relied on the old silence.

## 5. The First Remediation Broke the Build

Worth recording in full, because the lesson is more valuable than the defect.

The remediation for §3 was pushed after `gcc -fsyntax-only` on every modified
file, a green host suite, green TASM tests and green doc links. It broke **all
four** ESP-IDF builds on the first CI run:

```
goose_runtime.c:569:61: error: '%s' directive output may be truncated
writing up to 95 bytes into a region of size 40 [-Werror=format-truncation=]
```

The deferred telemetry buffer added in 3.1 is 40 bytes and was filled with a
bare `"%s"` from a 96-byte registry name. `-fsyntax-only` performs no code
generation, so it runs none of GCC's flow-sensitive analyses and could not
have caught it. **A syntax check is not a build**, and the verification section
of this document said as much while the change was pushed anyway.

The instinct was to write a stricter host compile and call it fixed. That was
tested rather than assumed, and it was wrong: the truncation diagnostic is
produced by the RISC-V toolchain and is missed by host GCC 11, 12, 13 and 14,
at every optimisation level, with `_FORTIFY_SOURCE` on or off. A host gate
would have been a false reassurance.

What actually closes the gap is running the real toolchain, which needs no
local ESP-IDF install — only the image CI already uses:

```bash
make idf-build     # docker run espressif/idf:release-v5.5
```

Confirmed both ways: with the defect reintroduced it reproduces CI's error
exactly; with the fix in place the build is clean.

Three gates came out of this round, each verified to fail on the defect it
defends before being trusted — the step skipped the first time:

| Gate | Defends | Proven by |
|---|---|---|
| `make idf-build` | the firmware build | reproduces the CI error on the reintroduced defect |
| `make warn-check` | `-Wall -Wextra -Werror` on the ESP-independent two thirds | found 3.11, 3.12, and a file that passes `-fsyntax-only` but fails at assembly |
| `make lock-check` | no telemetry inside the loom hold (3.1) | flags both original sites; clean on the fix |
| `make ci-lint` | workflow schema | names the dangling `needs:` that a job rename left behind |

`lock-check` needed a second attempt of its own. The first version tracked the
most recent loom call and reported clean on the real defect:
`fabric_alloc_internal` releases the lock inside an early-exit block whose text
precedes the still-locked region, so a linear scan believes the lock is
released for the rest of the function. It now saves held state on `{` and
restores it on `}`, which is what an early return actually means. Caught only
because the checker was tested against the bug instead of against the fix.

A fourth gate came from the same round, for the same reason. Renaming the
`format-check` job to `format-diff` left the `release` job's `needs:` list
pointing at a job that no longer existed. GitHub rejects that at parse time —
no jobs run, and the only feedback is "This run likely failed because of a
workflow file issue", which does not name the dangling reference. Reviewing the
job being edited was not enough; the file needed whole-file validation.
`make ci-lint` runs actionlint's schema check and reports the exact line.
Verified both ways, like the others.

Two further CI failures happened inside this remediation round, and they are
recorded rather than tidied away, because the pattern is the point. The first
was the dangling `needs:` above — no gate existed for it, and `ci-lint` is the
gate. The second was a guess: `pip install --prefix=/usr/local` in the new job,
which fails because pip appends its own `local` segment and the path resolves
to `/usr/local/local`. That one had no excuse — the replacement was verified in
an `ubuntu:24.04` container before pushing, which is what should have happened
the first time.

The through-line across all three breakages is the same: a check was trusted
because it was green, not because it had ever been shown to fail on the thing
it was supposed to catch. Every gate added here was made to fail first.

`make verify` runs all of it.

## 6. Open

- The `mesh status` / `mesh stat` counter set is now complete, but nothing enforces that a new
  arc op adds a TX counter. A future op can repeat 3.4.
- `validate_shell.py`'s outcome table is hand-maintained. It caught nothing in 3.2 because the
  wrong rows were absent, not because the rows present were wrong; the same shape of gap can recur.
- `atlas` sits at `observer` with no sub-command escalation. `atlas verify` walks the catalog
  without dereferencing hardware, so this is defensible, but it was not examined closely here.
- ~~The absent ESP-IDF build is the largest gap in this pass.~~ Closed: `make idf-build` runs the
  real toolchain in CI's own container image, and every change here is confirmed against a linked
  image (0 errors, 0 warnings).
- **No hardware was attached, and that is now the largest gap.** Two things rest on it. The loom
  fix (3.1) is reasoned from source and its figures come from this repository's own recorded
  measurements — the confirming experiment is `telemetry on` plus sustained `bonsai bloat` churn
  against a saturated fabric, comparing `goose_loom_hold_max_us` and watching for
  `LOOM_CONTENTION_FAULT` before and after. And the contract rows added to `validate_shell.py`
  have never been executed; the sanctuary probe is verified against the generated catalog and the
  guard predicate by hand, and the test now diagnoses a stale probe as a test fault rather than a
  firmware one, but that is reasoning, not a run.
- The tree still does not satisfy its own `.clang-format`. `format-diff` stops it getting worse
  and converges changed lines; bringing the existing ~9,000 violations into line is a deliberate
  reformat someone has to choose, and `goose_shadow_atlas.c` (7,203 of them) is generated and
  should probably be excluded from any such pass.
- `lock-check` defends one pattern textually. It says nothing about, for example, flash I/O under
  the loom — the class of `a249b2e` — which remains guarded only by review.
- `warn-check` covers the ESP-independent two thirds. The other 19 files are reached only by
  `idf-build`, at ESP-IDF's own warning level, which is less strict than `-Wall -Wextra -Werror`.
