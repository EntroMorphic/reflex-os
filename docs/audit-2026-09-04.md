Successor to [`audit-2026-08-12.md`](audit-2026-08-12.md). Assessment of the Reflex OS
codebase at commit `676f7fb`, after the Phase 1 shell-capabilities work and the
documentation sweep that followed it.

Every finding below was remediated in the same pass; each entry states what was
wrong, how it was confirmed, and what changed.

## 3. Findings

### 3.1 Telemetry performed blocking console I/O inside the loom lock — HIGH

`goose_runtime.c`, in `fabric_alloc_internal`: `goose_telem_evict` and `goose_telem_alloc` were
called while holding **both** `loom_authority` and `fabric_mux`. `reflex_critical_enter` is
`taskENTER_CRITICAL`, so this ran with interrupts disabled.

`goose_telem_*` writes to the console through `reflex_hal_write_raw`. On the C6 that is
`usj_write_bytes`, which spins on a USB-JTAG FIFO **per byte**, up to `USJ_TX_SPIN_LIMIT`
(20,000) iterations each, and returns early only when no reader is attached. On the ESP32 it is
`fwrite` + `fflush`.

The budget these two calls sat inside is `LOOM_LOCK_TIMEOUT_US = 300`, against the steady-state
peak hold of 353 µs recorded in `implementation-status.md`. A single console write is orders of
magnitude past that. The trigger condition is precisely when the Loom Viewer is in use and the
fabric is saturated — where every allocation also evicts, so two writes happen per allocation
under the lock. That is the `LOOM_CONTENTION_FAULT` class that commit `a249b2e` fixed for flash
I/O, reintroduced through a different door.

This was an outlier, not a design choice. Every other telemetry site in the substrate already
snapshots inside the lock and emits after unlocking — `internal_process_transitions` maintains a
`telem_defer_t` buffer for exactly this, and `goose_supervisor.c:651` carries the comment
*"serialised; the flash write must not hold it."* `reflex_hal_esp32c6.c` names the hazard directly:
a lock *"would have to be held across `usj_write_bytes` and therefore across a spin on a USB FIFO."*

**Fixed.** Both emissions now snapshot into locals inside the lock and emit after both locks drop,
matching the existing idiom. The snapshot is gated on `goose_telemetry_enabled`, so the default
(telemetry off) path costs nothing. The eviction name is copied — the registry entry is removed
moments later — into a 40-byte buffer, matching the documented telemetry name width rather than
widening the locked region's stack footprint.

> Note on the scheduler: the defect is not FreeRTOS-specific and the fix is not either. Blocking
> console I/O inside an interrupt-disabled critical section is wrong under any scheduler, including
> `reflex_task_kernel`. Nothing in the remediation adds a dependency.

### 3.2 The ternary outcome contract was incomplete — MEDIUM

`s_outcome` defaults to `SHELL_OK`, so any path that returns without calling `outcome()` reports
`#R:+1,ok`. Since `580a497` that marker is the SDK's contract — `AccessDenied` is keyed on it and
`ReflexNode.last_outcome` is the documented way an agent distinguishes *refused* from *ran and had
nothing to report*. Sixteen paths were answering that question wrongly.

**The Sanctuary Guard was the worst of them.** All three refusals in `goonies read` returned with
no outcome, so a guard that exists to stop an MMIO read from clearing status bits or popping a live
FIFO reported success while refusing. `shell_outcome.h` documents `SHELL_GUARD` as *"refused by a
policy guard (sanctuary, `sys.*`)"* — the enum value was written for this case and never emitted
for it. The gap was untested: `validate_shell.py` asserted `guard` only for `tapestry signal sys.*`.

The rest:

| Path | Was | Now |
|---|---|---|
| `goonies read` sanctuary refusal (×3) | `+1,ok` | `-1,guard` |
| `snapshot save` / `load` / `clear` | `+1,ok` regardless of `rc` | `-1,failed` on error |
| `mesh emit` / `query` / `posture` / `ping` / `peer add` | `+1,ok` regardless of `rc` | `-1,failed` on error |
| `config set boot_count <non-integer>` | `+1,ok` | `-1,invalid` |
| `mesh peer add` with wrong MAC separators | `+1,ok` | `-1,invalid` |
| `snapshot` / `purpose` bare usage | `+1,ok` | `0,usage` |
| `kernel` with no fields, `vm list` empty, `loom evictions` none | `+1,ok` | `0,none` |

The `rc`-printing handlers all predate the outcome marker: they print `rc=0x%x`, which tells a
human what happened and the SDK nothing. A single `outcome_rc()` helper now maps the code rather
than repeating the branch nine times. Contract cases for the guard, the parser rejections and the
usage paths were added to `validate_shell.py`.

### 3.3 `mesh peer add` silently truncated the peer name — MEDIUM

`reflex_peer_t::name` is 12 bytes; `strncpy` kept 11 characters and returned `REFLEX_OK`. The shell
then echoed back **`argv`**, not what was stored — so the confirmation line named a peer that
`mesh peer ls` would never show.

**Fixed** on the rule the goonies registry already follows for atlas names: an over-long name is
**refused**, not truncated. Both mesh-side callers are well inside the bound (DISCOVER carries at
most 8 bytes; auto-registration formats `auto_xxxx`), so nothing on the wire is affected. The shell
now names the limit on rejection and echoes the *stored* name on success.

### 3.4 `mesh status` totals omitted DISCOVER — LOW-MEDIUM

`rx_total` excluded `rx_discover`; `tx_total` was `tx_mmio_sync` alone, excluding the `tx_discover`
the struct already tracked and `mesh stat` already printed. A board broadcasting discovery beacons
since boot reported `tx=0`. This is the same omission `mesh stat` was fixed for — its handler
carries the comment explaining that leaving DISCOVER out *"reads as a dead mesh"* — applied there
and not here.

Worse, four ops had no TX counter at all, so README's "total RX/TX" claimed more than was measured.
**Fixed:** `tx_sync`, `tx_query`, `tx_advertise` and `tx_posture` added and incremented at each emit
site; both totals now cover every op; `mesh stat` prints the new counters.

### 3.5 `mesh_stats` was read under a lock its writers never took — LOW

`goose_atmosphere_get_stats` acquired `swarm_mux` to copy the struct. Not one of the thirteen
`mesh_stats.*++` sites held it — they run in the radio receive callback. The lock protected nothing
while reading as though the snapshot were serialised, which is worse than no lock at all. The
increments are read-modify-write, so a preemption between load and store drops one outright, and on
the dual-core ESP32 the two can genuinely race.

**Fixed** with `__atomic_fetch_add(..., __ATOMIC_RELAXED)` per counter and the misleading lock
removed from the getter. Relaxed is the correct model: these counters carry no happens-before
relationship to anything, they are only observed for their own value. Each field is a
naturally-aligned `uint32_t` so no counter reads torn; the snapshot as a whole is not one instant,
which is the right trade for observability and is documented as such.

### 3.6 A peer rename never reached NVS — LOW

`goose_mmio_sync_add_peer` called `peers_save_nvs()` only when appending. Re-adding a known MAC
under a new name updated RAM and returned OK, so the rename held until the next reboot and then
silently reverted. **Fixed:** the update path persists when the name actually changed.

### 3.7 Stale comment on the Aura fail-closed path — LOW

`calculate_aura` documented its sentinel as guarding against *"any mbedtls error."* mbedtls was
removed in the crypto consolidation (`979fbbb`); the MAC comes from `reflex_crypto.c`, which cannot
currently fail — so the branch is defence in depth, not a live path. The comment also still
described the retired 32-bit MAC width. **Corrected.** The branch is kept deliberately: an aura that
silently degrades to a predictable value is exactly the failure it must never have.

### 3.8 README's line count did not reconcile — DOC

README claimed "~26,000 lines of C and assembly." Measured: **16,044** hand-written (C/H/S,
excluding tests and the generated atlas), **28,822** including the atlas, **31,545** including
tests. No natural counting produced ~26,000. **Corrected** to state both figures and which is which.

### 3.9 The crypto suite tested determinism, not correctness — MEDIUM (test gap)

`test_crypto` asserted that the MAC was deterministic and that it changed when the key or message
changed. All three hold for an implementation that computes the *wrong* digest. Because both sides
of a mesh run this same code, a wrong-but-consistent SHA-256 would have authenticated every arc
between two boards happily while being incompatible with every other HMAC-SHA-256 in existence —
and no test in the tree would have noticed.

The implementation is in fact **correct**: verified byte-for-byte against OpenSSL across key lengths
1–140 and RFC 4231 cases 1, 2, 3, 6 and 7. The gap was in the testing, not the code.

**Fixed:** the RFC 4231 known-answer vectors are now asserted, including case 6 — a 131-byte key,
which exercises the `key_len > 64` branch that folds the key through SHA-256 first and which nothing
had ever executed. A 16-byte case matching the Aura key width is included, cross-checked against
OpenSSL since the RFC has none. Host suite: 350 → 355.

### 3.10 Implicit declaration of `malloc` — LOW

`goose_runtime.c` calls `malloc` without including `<stdlib.h>`, reaching it transitively under
ESP-IDF. Implicit declaration is an error from C11 onward and would truncate the pointer on any
64-bit host build. **Fixed** with the include.

## 5. Open

- The `mesh status` / `mesh stat` counter set is now complete, but nothing enforces that a new
  arc op adds a TX counter. A future op can repeat 3.4.
- `validate_shell.py`'s outcome table is hand-maintained. It caught nothing in 3.2 because the
  wrong rows were absent, not because the rows present were wrong; the same shape of gap can recur.
- `atlas` sits at `observer` with no sub-command escalation. `atlas verify` walks the catalog
  without dereferencing hardware, so this is defensible, but it was not examined closely here.
- The absent ESP-IDF build is the largest gap in this pass. Nothing above is confirmed against a
  linked image.
