## 1. Scope and Method

Four parallel review passes over the whole tree — VM/kernel/core, GOOSE substrate,
shell + wireless attack surface, Python tooling/SDK — then **every finding at HIGH or
above was independently re-verified** by reading the code, executing the tool, or
compiling the real translation unit against a probe. Findings that could not be
reproduced on re-check were dropped or downgraded, and are noted as such.

Build/test state at audit time: host suite **350/350 pass**, TASM suite pass, 6 CI jobs
green. Firmware builds were *not* re-run in this pass (no hardware attached);
everything below is static analysis plus host execution.

| Depth | Areas |
|---|---|
| **Read in full** | `vm/loader.c`, `vm/mmu.c`, `vm/cache.c`, `vm/ternary.c`, `vm/interpreter.c`, `vm/task_runtime.c`, `goose_library.c`, `goose_lattice.c`, `goose_registry.c`, `goose_atmosphere.c` (RX path), `reflex_crypto.c`, `shell_policy.c`, `shell_parse.c`, `loomc.py`, `tools/tasm.py`, `sdk/python/reflex.py` |
| **Targeted analysis** | `goose_runtime.c`, `goose_supervisor.c`, `kernel/`, `core/`, `platform/esp32c6/`, `storage/`, `net/`, `services/`, `tools/loom_viewer.py`, `tests/hardware/validate_shell.py` |
| **Skipped on purpose** | `goose_shadow_atlas.c` (12,778 lines, SVD-generated; verified structurally, not by eye) |

## 2. Findings, Ranked

Severity × reachability. Each entry names the exact location and the failure it
produces. IDs continue the `P0-` prefix from the filename for unambiguous reference in
future commits and changelogs.

### P0-H1 — VM loader validates the TSYS syscall selector at 16 bits while decoding at 17
**`vm/loader.c:23`** (`static bool reflex_vm_loader_syscall_valid(int16_t imm)`),
consumed at **`:150`**. **HIGH. Verified by compiling the real `loader.c` against a
probe.**

This is the same defect class already fixed and documented for branch targets — the
comment at `loader.c:28-37` explains that the decoder produces a *17-bit signed*
immediate and that `int16_t` truncation is a hole — but the identical pattern two
checks away was left as `int16_t`. Both directions are live:

- **Accepts what it should reject:** an in-memory/v1 image with `imm = 0x10003`
  truncates to low-16 `3` (`REFLEX_VM_SYSCALL_DELAY`), passes validation, and the
  interpreter then dispatches on the full `65539`.
- **Rejects what it should accept:** a *packed* (wire) image with a syscall selector
  in `4..65538` sign-extends to a negative `int32_t`, and the truncated range check
  `imm >= REFLEX_VM_SYSCALL_LOG` refuses it. `vm loadhex` (`shell.c:1341`) is the
  only user-reachable input path, so any forward-compatible syscall ID ≥ 4 is
  unloadable over the wire.

One-line fix: `int16_t imm` → `int32_t imm`. Then pin with a regression test in
`tests/host/test_vm_regress.c` alongside the branch-target case.

### P0-H2 — LoomScript loader copies `orientation` and `coupling` from wire bytes with no validation
**`components/goose/goose_library.c:192-193`**, inside `goose_weave_loom`.
**HIGH. Verified by reading.**

The 2026-08-12 pass hardened this parser *structurally* (counts, indices, buffer
lengths — all now correct), but the per-route payload fields are copied straight
through: `r->orientation = re.orientation` (arbitrary `int8_t` into a `reflex_trit_t`,
so a hostile fragment can store e.g. `7`) and `r->coupling = re.coupling` (arbitrary
`uint8_t`, and **`GOOSE_COUPLING_RADIO` is honored** — each such route fires
`goose_atmosphere_emit_arc` from a `GOOSE_RHYTHM_REACTIVE` 100 Hz pulse task, inside
the loom hold that `implementation-status.md` already flags as a known pressure
point). Quotas bound the blast radius (8 fragments × 32 routes), but a single
admin-role upload can weave a permanent radio-transmit loop with no weaver-visible
error.

Adjacent gap in the same parser: **`head.trans_count` is parsed at `:120-137` and
then silently ignored** — a fragment declaring transitions parses cleanly and loses
them. The header comment says every field is "treated as hostile until proven
otherwise"; these are not.

Fix: clamp `orientation` to `{-1,0,+1}` (reject otherwise), whitelist `coupling` to
`GOOSE_COUPLING_SOFTWARE`, and reject `trans_count != 0` until a transition format is
implemented. Feeds directly from P0-H4, which is how a semantically-wrong fragment
would be produced.

### P0-H3 — `goose_supervisor_rebalance` mutates routes and runs a propagation pass with no loom lock
**`components/goose/goose_supervisor.c:392-407`**, called from `goose_supervisor_pulse`.
**HIGH (dual-core), LOW (single-core). Verified by reading.**

The supervisor's own discipline — "the pulse path holds `loom_authority` for the
duration of `internal_process_transitions`" — is violated here: `rebalance` writes
`r->orientation = REFLEX_TRIT_POS` *outside* the lock, then calls
`goose_process_transitions(field)` at `depth == 0`, which takes the lock. On the
single-core C6 this is benign (the supervisor cannot preempt itself mid-write). On
the dual-core ESP32, the supervisor task (priority 20) and a field pulse task
(priority 10, unpinned) genuinely run in parallel, so the orientation write races the
pulse's route reads in `internal_process_transitions` and `check_equilibrium`
(`:379-386`). Narrow window in today's small static fields, but the function exists
to repair stuck fields at runtime.

Fix: take `goose_loom_try_lock` (with the established timeout-and-skip semantics)
around the mutation + propagation, matching every other route mutation site.

### P0-H4 — `loomc.py` crashes on malformed input and reports success on a typo'd verb
**`tools/loomc.py:21-24`** and the missing `else` after the `weave` branch.
**HIGH. Reproduced on this machine.**

```
$ printf 'weave a\n' > bad.ls && python3 tools/loomc.py bad.ls bad.loom
IndexError: list index out of range          # parts[1] on a line with no '->'

$ printf 'route x -> y\n' > typo.ls && python3 tools/loomc.py typo.ls typo.loom
Success! Fragment woven into typo.loom (0 routes).   # a misspelled verb is silently dropped
```

A misspelled directive emits a *valid but empty* fragment, and the compiler prints
"Success!" — so a broken LoomScript source produces an artifact the firmware accepts
and weaves to nothing. `line.replace("weave ", "")` also scrubs the substring from
*inside* cell names (`weave weave x -> y` corrupts the name), and `cname[:23]`
silently truncates long names so two distinct cells alias onto one entry. This tool
is the producer side of P0-H2's trust boundary.

Fix: parse with a real split, reject unknown verbs with a non-zero exit, terminate on
missing `->`, and refuse names over the 23-byte wire width rather than truncating.

### P0-M1 — Mesh replay-cache slot index ignores the sender MAC; the comment says otherwise
**`components/goose/goose_atmosphere.c:134-139`** (`replay_slot_index`).
**MEDIUM. Verified by simulation.**

```c
uint32_t h = nonce ^ ((uint32_t)mac[4] << 16) ^ ((uint32_t)mac[5] << 8);
return h & (REFLEX_REPLAY_CACHE_SLOTS - 1);   /* SLOTS = 64 → mask 0x3F */
```

The blend term places both MAC bytes at bit positions 8–23; the mask keeps the low 6
bits. The slot is exactly `nonce & 63` for *every* sender. Nonces are
`(uint32_t)reflex_hal_time_us()` — monotonic and roughly predictable. A second
legitimate peer whose uptime is 64·k µs ahead, or a key-holding attacker, evicts a
victim's slot with a crafted nonce, and `replay_seen_or_record` then accepts a
replayed copy of the victim's earlier arc inside the 5-second window. This is a
correctness hole in a security mechanism [`../SECURITY.md`](../SECURITY.md) §7 claims
is working, not a memory-safety issue.

Fix (one line): fold the MAC into the low bits, e.g.
`h ^= (uint32_t)(mac[4] ^ mac[5]) * 0x9E3779B1u;` before masking, so code matches
comment. Pin with a host test that two MACs sharing nonce low-bits land in different
slots.

### P0-M2 — `make format-check` (and therefore CI's format gate) always passes
**`Makefile:60-62`**. **MEDIUM. Verified by reading.**

```make
format-check:
	@find ... | xargs clang-format --dry-run --Werror 2>&1 | head -20
	@echo "Format check passed."
```

`clang-format`'s exit status is consumed by the pipe to `head` (no `pipefail`), and
the `echo` runs unconditionally — so the target succeeds whether or not formatting is
violated, and the `format-check` CI job is green-by-construction. Every other CI gate
in `.github/workflows/build.yml` is real; this one is not.

Fix: `set -o pipefail;` (or drop the `| head -20` and let the error propagate), and
only `echo` on success.

### P0-M3 — The system VM's soft cache is installed and then silently erased before first use
**Order of operations across `main/main.c:165-166` and `vm/task_runtime.c:204`**.
**MEDIUM. Verified by reading both call sites.**

`main.c` runs `reflex_cache_init(&system_cache)` then
`system_vm.vm.cache = &system_cache` (line 165) — and *then* calls
`reflex_vm_task_register_service(&system_vm, …)` (line 166), whose
`service_register → desc.init` path is `reflex_vm_task_service_init`, which calls
`reflex_vm_task_runtime_init(runtime)` → `memset(runtime, 0, sizeof(*runtime))`.
The cache pointer is zeroed back to NULL and the system VM runs in direct-MMU mode —
all TLD/TST/TFLUSH/TINV cache semantics are skipped, with no diagnostic.
Not memory-unsafe (NULL cache is a supported mode), but a shipped feature that is
never active, and a trap for anyone who builds on the assumption that it is.

Fix: install the cache *after* `register_service`, or make
`reflex_vm_task_runtime_init` preserve a caller-set cache field.

### P0-M4 — VM task self-delete leaves a narrow stop→restart lifetime gap
**`vm/task_runtime.c:58-62` → `:162`**. **MEDIUM (timing-dependent), suspected.**

`reflex_vm_task_entry` sets `runtime->handle = NULL` and then calls
`reflex_task_delete(NULL)`, which under ESP-IDF means `vTaskDelete(NULL)` = delete
the *calling* task. The handle-clear is what lets `reflex_vm_task_stop`'s completion
wait (`while (runtime->handle != NULL)`) see the task as gone — but
`vTaskDelete(NULL)` defers the actual TCB/stack teardown to the idle task, so a
watcher (e.g. the service watchdog restart path in `core/service_manager.c:163-164`)
can observe `handle == NULL` and immediately re-call `svc->start →
reflex_task_create`, reusing `runtime` while the prior VM task's resources are not
yet reclaimed. The comment block at `task_runtime.c:170-179` documents the unbounded
hang the current shape was built to avoid; this is the subtler lifetime traded for
it. Today only the watchdog hits it, and no test exercises stop→restart of a VM
task. Fix: signal completion from the entry *before* self-delete via a semaphore or
event bit, rather than via the handle field.

### P0-M5 — `tasm.py` robustness cluster (reproduced)
**`tools/tasm.py`** — five separate defects, all confirmed by executing the tool.
**MEDIUM.**

- **`:82`** — bare `.entry` on a line raises `IndexError` (`line.split()[1]`), not a
  diagnostic.
- **`:84`** — duplicate labels silently overwrite: `start: … start:` assembles
  cleanly and resolves every reference to the *second* definition, with no error.
- **`:101`** — error line numbers index the pass-2 instruction list, so after any
  label/comment/blank line the reported line is wrong (a fault at source line 5
  reports as `Line 0`).
- **`:298`** — `tasm.py in.tasm --upload` with the port omitted falls through to
  `assemble(in, "--upload")` and creates an output file literally named `--upload`.
- **`:259-294`** — `upload()` has no `try/finally` around the serial port, so any
  exception between open and close leaks the fd, and the fixed `time.sleep(1.5)` +
  `read(in_waiting)` races a slow board, reporting a false failure on a timing miss
  alone.

Each is one-to-three lines. The immediate-range check at `:211-215` (a past real bug)
shows the bar this tool already holds — these five are below it.

## 4. Verified Clean

Checked hard, nothing found — recorded so the next pass does not re-spend the effort:

- **The open-addressed hash indexes** (`goose_lattice.c`, `goose_registry.c`) — the
  backward-shift deletion, wrap-around cyclic condition (Knuth 6.4R), and registry
  swap-remove were hand-walked and match the differential tests. Correct.
- **Loom-lock pairing and ordering** — every `goose_loom_try_lock` success is matched
  by exactly one unlock; order is uniformly `loom_authority → fabric_mux`, never
  reversed, never from ISR.
- **`vm/mmu.c`** — region add and translate bounds are overflow-safe; no bypass found.
- **`vm/cache.c`** — the historical TINV discarding-invalidate is fixed and test-pinned.
- **Ternary arithmetic** — word18 pack/unpack guards, `from_int32` scratch-then-publish,
  add/sub carry, `to_int32` range: all sound.
- **`shell_parse.c` / `shell_policy.c`** — hex and int parsers reject all malformed
  input before writing; role policy is fail-closed with 23/23 dispatch entries present.
- **`reflex_crypto.c`** — HMAC-SHA256 passes RFC 4231 cases 1/2/6, the 64-byte boundary,
  and empty input; the Aura fail-closed sentinel is sound.
- **802.15.4 RX path** — frame and payload lengths are validated before parse; self-arc
  suppression happens at the radio layer by source address.
- **SDK injection surface** — every structured helper routes through `_token`, which
  rejects *all* whitespace; `raw()` is the documented escape hatch. No newline smuggling.

## 5. Suggested Order

The top four are independent, each targeted by the existing host suite, and none touch
the lock discipline the rest of the system depends on — a single low-risk batch:

1. **P0-H1** — one line + regression test (highest payoff-to-risk ratio in the pass)
2. **P0-M1** — one line, restores a guarantee SECURITY.md already claims
3. **P0-M2** — two lines, un-lies the CI format gate
4. **P0-H2** — clamp + whitelist + reject, closes the semantic side of the parser
5. **P0-H3** — add the missing lock around `rebalance`
6. **P0-H4 / P0-M5** — the tooling robustness batch (developer-facing, not hardware)

P0-M3 and P0-M4 are correct-as-shipped bugs worth scheduling but safe to defer past
the above.
